## 1. Vision

BlindVault is a **local-first** encrypted personal vault for any kind of private information. It runs entirely in the browser, can be installed as a PWA, and **has no server that stores user data**. It is intentionally not a cloud password manager: there is no account system and no server-side vault.

> The user's vault belongs to the user, not to a service.

Data exists only on the user's devices or in encrypted backup files the user controls. Synchronization is peer-to-peer between registered devices, each admitted through SAS-confirmed pairing.

BlindVault is derived from BlindPass: it reuses the cryptographic model and domain packages, and removes the server, database, sessions, API and administration layers (section 15).

**v1 success criterion:** a user can create a vault, protect it cryptographically, recover it after losing local storage, pair another device without trusting a server, synchronize safely, and understand exactly what happens if every device except the backup is lost. The criterion is not feature count.

**Highest-priority engineering risks**, in order: pairing protocol correctness, application/PWA integrity, browser storage behavior, recovery UX, and synchronization edge cases. None of them requires abandoning the architecture, but cryptography, pairing, synchronization and recovery MUST be implemented as explicit protocols rather than informal application logic. The project SHOULD resist adding features before these foundations are thoroughly tested.

## 2. Principles

1. **No data server.** BlindVault MUST NOT require a server to store vault data, which minimizes the attack surface. Network services are used only for static assets and STUN. None of them receive plaintext vault contents, and STUN providers MUST NOT be treated as trusted data services.
2. **Encryption first.** All sensitive content is encrypted before persistence or synchronization. Keys exist in plaintext only in memory, while the vault is unlocked; every key at rest is wrapped or encrypted, and the Master Key is at rest only inside local wraps, the Recovery Envelope and backups.
3. **Local-first.** A browser/PWA application keeps the vault local and portable. Once installed, the app works offline. There is no account, backend, authentication server, cloud database or sync service.
4. **Synchronization is replication**, not a hosted backup service. Every registered device holds a complete encrypted copy of the vault. A `.bvault` file is an additional recovery mechanism.
5. **Small attack surface.** Few dependencies, small security-sensitive modules, clear cryptographic boundaries, deterministic builds, extensive tests, and no unnecessary network functionality.
6. **Generic model.** BlindVault is a vault, not only a password manager. Items are made of typed fields. Templates are a UI convenience and MUST NOT alter the cryptographic model.

## 3. Threat model

**Protected assets:** vault contents, secrets, passwords, credentials, recovery material, cryptographic keys, encrypted backups and synchronized records.

**Threats considered:** loss or theft of a device, access to a locked device, network interception, malicious peers, MITM during pairing, compromised STUN, corrupted sync data, browser storage eviction, accidental deletion, stale devices reconnecting, and malicious application hosting.

**Out of scope (MUST be documented to users):** a compromised operating system, malware that reads browser memory, malicious extensions, an attacker holding an unlocked device, keyloggers, a malicious browser, and a malicious JavaScript bundle executed before integrity verification, including the first load (TOFU, see D5).

Cryptographic confidentiality and application integrity are separate properties. A malicious bundle can read vault contents after unlock, even with perfect cryptography; a compromised browser, OS, extension or JavaScript bundle can therefore compromise an unlocked vault and is outside the cryptographic threat model.

**Accepted metadata leakage.** The cleartext record header (section 6) is visible to anyone who can read IndexedDB on a locked device: record types and counts, `keyEpoch`, deletion state, and the HLC of every change (which reveals editing times and the `deviceId` that made them). The header is readable but authenticated (D21), so it cannot be altered without detection. During sync the same header is visible to the peer, never to the network. The cleartext part of Local Config (section 6) is also readable: `vaultId`, the random `localConfigId`, which reveals nothing (D121), the KEK salt and parameters, whether WebAuthn unlock is set up (D58), and, only while a vault replacement is unfinished, the `vaultId` of the vault being replaced, which shows that a re-founding or a restore of a different vault took place (D96). An Item Version's header `hlc` equals an `hlc` its item held earlier, so someone who reads the storage at two different times can link versions to their items and count each item's edits, even though `itemId` is encrypted (D6). A `.bvault` file hides all of it (section 10), except the `phraseId` and the phrase creation date in its header, which link backups of the same vault to each other and date the phrase; the header also shows the format version and whether the backup has an export-password keyslot, and the file size reveals the vault's approximate size. After v1, an installation holding several vaults also shows, before unlock, how many vaults it holds and the Vault nickname of each (D79). Record ciphertext lengths are also readable; record content is padded to a multiple of 256 bytes before encryption, so a length reveals only a size bucket, not the length of an item or a secret (D92).

**Storage rollback (D77).** Replacing a device's whole storage (IndexedDB and Local Config together) with an earlier copy of itself cannot be detected, since every record in the copy authenticates. It can be benign (an OS, browser-profile or VM restore) or done by someone who held the locked device at two different times. The device loses the changes that existed only on it since the copy and may show notices again; at its next sync, the newer records and tombstones held by peers win again by LWW, and peers that hold a retirement keep refusing the retired device. This is accepted. Cloning the storage into a second installation that runs alongside the original (a copied browser profile, a cloned VM) is different: both copies share one device identity and can issue the same HLC for different writes, which then never converge (section 9.2). This is also accepted and undetectable; user documentation MUST say that a cloned installation is replaced by pairing (D87, D153).

**Device admission.** BlindVault creates a Device record only for the vault creator at vault creation or re-founding (D40), and otherwise only after SAS confirmation in pairing or re-admission (D30); the only later changes to a Device record are its display name and its `retired` flag (D26, D31). Anyone holding the Vault Key can still forge a Device record and introduce it by sync or backup merge, which lets a retired device return under a new identity; a Master Key holder can also retire every other device. This is accepted, since holding the Vault Key already grants full access to the vault, but both are made visible to the user (D47, D48) and the response is re-founding (D28).

## 5. Cryptography

### 5.1 Primitives

Primary implementation: **libsodium** (`libsodium-wrappers-sumo`). Primitives: Argon2id, XChaCha20-Poly1305 (AEAD), X25519, `secretstream`, `crypto_kdf`, BLAKE2b, sealed boxes (`crypto_box_seal`, X25519 + XSalsa20-Poly1305) for the backup's recovery keyslot, IETF ChaCha20-Poly1305 inside Noise `ChaChaPoly`, and a secure RNG.

Two more primitives serve item features only and never protect vault data: `crypto_secretbox` (XSalsa20-Poly1305), used only to decrypt a BlindPass `.blindpass` export during import (D126), and HMAC-SHA1, HMAC-SHA256 and HMAC-SHA512 from WebCrypto (`crypto.subtle`), used only to compute TOTP codes (D127).

Custom cryptographic primitives MUST NOT be implemented. Protocols (Noise) MUST come from an existing, validated implementation (D1). The Noise handshake state machine is copied from `noise-protocol` into `packages/crypto` with its primitives bound to libsodium (D200), and it stays acceptable only while it passes the official test vectors for both patterns in CI (D157).

### 5.2 Key hierarchy

```
Local password ──Argon2id──► Device KEK ─────────┐
WebAuthn PRF (optional) ───► PRF KEK ────────────┤
Recovery Phrase ─crypto_kdf─► Recovery KEK       │
    ├─ envelope subkey (Recovery Envelope) ──────┴──► unwraps ──► Master Key
    └─ keyslot subkey ──► Recovery keyslot keypair (D16):             │
         public key synchronized, private key                         │ crypto_kdf subkeys only (D23)
         derived only from the phrase                                 ├─► Vault Key wrapping subkey ──► Vault Key (per keyEpoch)
                                                                      │                                     │ wraps
                                                                      │                                     ▼
                                                                      │                                 Record key (per record)
                                                                      │                                     │ AEAD
                                                                      │                                     ▼
                                                                      │                                 Encrypted record content
                                                                      ├─► version-ID subkey ──► versionId (D6)
                                                                      ├─► re-admission subkey ──► key-confirmation MAC (D29)
                                                                      └─► Local Config subkey ──► encrypted part of Local Config,
                                                                                                    including the Device Identity (D58, D67)
```

The Master Key is never used directly as an encryption key: every use derives its own `crypto_kdf` subkey with a distinct subkey ID (D23).

### 5.3 Keys

**Master Key.** Root of the vault, identical on all devices, which is what makes device replication possible. Generated by a CSPRNG. MUST NOT be persisted directly, synchronized in plaintext, or stored directly in IndexedDB. Exists in plaintext only in memory while unlocked. Not rotated in v1 (D11). Used only through `crypto_kdf` subkeys, one per purpose: Vault Key wrapping, `versionId` derivation, re-admission key confirmation, and Local Config encryption, which also protects the device identity (D23, D29, D58, D67).

**Device KEK.** `KEK = Argon2id(password, local salt, local parameters)`. The salt, parameters, wrapped Master Key, PRF KEK material and security preferences are local and MUST NOT be synchronized. Each device may have a different password, so each device's security is independent. Changing the password on one device MUST NOT require synchronization and only re-wraps the Master Key. It MUST require the current local password, checked by opening the Master Key wrap with it, so someone holding the unlocked device cannot set a password of their own; a user who forgot it uses the Recovery Phrase (D168). Parameters are **calibrated on the device** whenever a local password is set (vault creation, pairing, fresh restore, re-founding, password change), targeting about 1 s, with a **64 MiB memory floor** (D9). The application MUST reject a local password that fails the strength check (zxcvbn or equivalent), as the export password must (D36, D65), since a weak local password on a lost device is a Master Key compromise (section 14). The local password MUST reach a zxcvbn score of 4 (an estimated 10^10 guesses or more) (D71); the export password MUST reach an estimated 10^14 guesses or more, read from zxcvbn's guess estimate rather than its score, since its backup can be attacked offline wherever the file is copied (D134); a passphrase taken unchanged from the password generator is judged by its exact entropy instead (D155). Either threshold MAY be met by the equivalent estimate in a replacement library. Strength checks MUST NOT be treated as cryptographic protection. Wherever a local password is set, the UI MUST state that letting the browser save it can make a copy of the browser's data enough to open the vault (D175).

**Vault Key.** Random (not derived from user credentials), protected by the Master Key, always tagged with a `keyEpoch` so the key can be rotated later without redesigning the record format.

**Record key (D18).** Random and independent per content record (Item, Item Version, Folder, Device, and the Recovery Envelope's metadata, D24), wrapped by the Vault Key of the record's `keyEpoch` with the record's AAD, and stored in the record. Because the AAD includes `hlc` and `deleted` (D21), the record key is re-wrapped on every write. Record keys give record isolation, independent encryption contexts, simpler future rotation, and safer handling of deleted or migrated records. Two keys are not protected by a record key: the Vault Key, wrapped by the Master Key's Vault Key wrapping subkey, and the Master Key inside the Recovery Envelope, wrapped by the Recovery KEK envelope subkey (D24).

### 5.4 Recovery Phrase (D2)

- 256 bits from a CSPRNG, displayed as a 24-word BIP39 phrase. In the UI it is called "Recovery Phrase", never "seed": it represents vault recovery entropy, not a cryptocurrency wallet.
- `Recovery KEK = crypto_kdf_derive_from_key(entropy, fixed context)`. No Argon2, since entropy is already high. The Recovery KEK is never used directly: each use derives its own `crypto_kdf` subkey with a distinct subkey ID (key separation).
- The **envelope subkey** wraps the Master Key. This Recovery Envelope is a **synchronized record** with a fixed `recordId` per vault, merged by LWW, so every device and future backup holds the current envelope.
- **Recovery keyslot keypair (D16).** A second subkey seeds an X25519 keypair (`crypto_box_seed_keypair`). The Recovery Envelope also carries the **public key** in its metadata, which is encrypted with a record key wrapped by the Vault Key, not with a phrase-derived key (D24). Any unlocked device can therefore read it and create a backup's recovery-phrase keyslot (`crypto_box_seal` of the file key) without holding the phrase or any recovery secret. The private key exists only while the phrase is being used.
- Each phrase has a random `phraseId` and a creation date, stored in the Recovery Envelope and in every backup header, and shown to the user when the phrase is generated, when a backup is listed, and when a backup is restored ("opens with the Recovery Phrase from 2026-10-06").
- Combined with a `.bvault` backup, the phrase MUST be sufficient to recover the vault. It MAY be used to set a new local password on a device; it then opens the Recovery Envelope held on that device, so after a regeneration it works there only once the device has received the new envelope, and until then only the old phrase does. The vault stays locked: the Master Key the phrase opens is proved by opening this device's Local Config, every record is read as at unlock, and only the Master Key wrap is rewritten (D184).
- Shown only once, at creation or regeneration, with confirmation that it was written down. The entropy is never stored, so the phrase cannot be shown again. MUST NOT be persisted or logged in plaintext. The confirmation asks for the words at three positions drawn at random, and a wrong answer shows the phrase again; the phrase screen offers no copy or download, since the clipboard and downloaded files are outside the app's control, and warns that a screenshot or photo lands in the device's gallery and its cloud backup (D179).
- **Check Recovery Phrase:** while unlocked, the user can type the phrase and the app confirms whether it opens the current Recovery Envelope and whether the envelope's recovery keyslot public key is the one derived from the phrase. A mismatched public key means backups cannot be opened with that phrase, and the UI MUST say so. The check also compares the Master Key the envelope yields with this vault's, and a vault whose envelope is missing or failed verification is told so instead of being asked for the phrase (D180).
- **Regeneration:** with the vault unlocked, a new phrase and a new envelope replace the current envelope; this MUST NOT require changing vault contents. The new envelope reaches other devices only when they sync, and the UI MUST show that the new phrase is not yet on other devices. If two devices regenerate concurrently, LWW keeps one envelope; a device that receives an envelope newer than the one it created MUST warn the user that the phrase they wrote down was superseded; the warning names that phrase by `phraseId` and creation date, states that backups made with it since its regeneration open only with it, tells the user to keep it until a new backup exists, and offers to make one at once (D145). Every other device whose held envelope, after a merge, has a `phraseId` that differs from the last one it has seen MUST show a one-time notice that the Recovery Phrase was regenerated, with its creation date, that new backups open only with the new phrase, and an offer to Check Recovery Phrase (D43); this also exposes a regeneration made by a device that should not have made it, such as a retired one. A device that has no `phraseId` recorded yet records the first one it receives, in pairing or a fresh restore, without a notice (D48). An envelope cannot be replaced without a new `phraseId` (D44, section 9.2), so no replacement escapes this notice. Regeneration is blocked while the held Recovery Envelope is read-only because its HLC is beyond the future-clock bound, and the UI shows when it becomes possible (section 6, D74). It is also blocked while the held Recovery Envelope's metadata holds content the app does not know, and the UI tells the user to update the app (D98). It is also blocked for a vault without a Recovery Envelope (D179), and allowed over one kept aside as corrupt at unlock, which it replaces (D185). Like an export, regeneration asks again for the local password, or a passkey assertion with user verification, and opens the Master Key wrap with it, since the unlocked session holds no Master Key and the new phrase yields it (D181, D185); the phrase and its confirmation come first, as at creation (D179), and one commit writes only the new envelope and the new `phraseId` as the last one seen. After regeneration the UI MUST prompt for a new backup at once, since existing backups open only with the old phrase; until a backup is made on this device after the current phrase's creation date, Settings says no backup made here opens with it (D185). A `phraseId` is shown as its first 8 hex digits next to the phrase's creation date (D185). The superseded-phrase warning replaces the one-time notice on a device whose own envelope, the one whose `hlc` carries its `deviceId`, loses to another `phraseId`, in a backup merge now and in sync later (D185). **Documented limitations:** older `.bvault` backups can still be opened with the old phrase, and a device that has not yet synced keeps producing backups for the old phrase; the `phraseId` shown with every backup makes this visible.
- **Regeneration is for a lost phrase, not an exposed one.** Anyone holding an old phrase can open any backup made for it, the Recovery Envelope of any device that has not yet received the new one, or any earlier copy of a device's storage, and so obtain the Master Key, which regeneration does not rotate (D11). An exposed phrase is a Master Key compromise (section 14), and the regeneration UI MUST say so.

### 5.5 WebAuthn PRF

Optional, for convenient local unlock, and detected at runtime. Derives a PRF KEK that wraps the Master Key. It does not replace the hierarchy. Password unlock always remains available. Without support, the app falls back to the password gracefully.

The credential MUST be created and used with `userVerification: "required"`, and the app MUST reject an assertion whose authenticator data does not report user verification, never deriving the PRF KEK from it (D75). With WebAuthn unlock set up, a lost device is protected by the authenticator's user verification (device PIN, biometric or security-key PIN) instead of the local password and Argon2id; the setup UI MUST say so. Setting it up, or replacing the passkey, MUST require the current local password, checked by opening the Master Key wrap, as a password change does, so someone holding the unlocked device cannot add a passkey of their own; removing it needs nothing more, since it only takes a way to unlock away (D172). A passkey unlock never sets a new local password: without the current one, only the Recovery Phrase does (D173).

A passkey synced by the platform (iCloud Keychain, Google Password Manager) carries its PRF secret to the platform account, so whoever controls that account and holds a copy of the locked storage can unlock the vault without the device. At setup the app reads the backup-eligible (BE) flag of the authenticator data; when it is set, the setup UI MUST state that the vault then also depends on the security of that platform account (D84). Such credentials are accepted.

Erase, re-founding and every replacement of the vault, by pairing or by restore (D150, D153), delete the PRF wrap but not the credential, which stays in the authenticator or platform account and can no longer unlock anything. Afterwards the app SHOULD ask the authenticator to remove it with `PublicKeyCredential.signalUnknownCredential` where the browser supports it, and otherwise tell the user the passkey can be deleted by hand (D120).

### 5.6 AAD and nonces

Every encrypted record MUST bind its ciphertext to its logical identity through AAD, so ciphertext from one record cannot be substituted for another's:

```
AAD = recordFormatVersion || recordType || vaultId || recordId || keyEpoch || hlc || deleted
```

The fields come from the record header (section 6), except `vaultId`, which comes from Local Config. The same AAD binds the wrapped record key, the Vault Key record and the Recovery Envelope (D8, D18). Binding `hlc` and `deleted` (D21) means the whole cleartext header is authenticated: a header cannot be edited to win LWW, to delete a record, or to replay older ciphertext as a newer write. Local wraps, which are not records (the Master Key under the Device KEK or the PRF KEK, and the encrypted part of Local Config, which holds the device identity, under its Master Key subkey, D58, D67), use `AAD = versioned purpose label || vaultId || localConfigId`, so a wrap cannot be moved to another purpose, another vault or another device of the same vault (D121). Nonces follow libsodium requirements: random 24-byte nonces for XChaCha20-Poly1305 and `secretstream` for large data. Nonce reuse under the same key MUST NOT occur.

### 5.7 Serialization and versioning (D10)

- **AAD, transcripts and prologues:** fixed binary layout, every field length-prefixed in a fixed order. No dependencies, with test vectors.
- **Records and protocol messages:** deterministic CBOR (RFC 8949, §4.2). The decoder is strict and rejects non-canonical encodings.
- No binary or textual representation may have multiple equivalent encodings that could produce different cryptographic transcripts.
- **Record padding (D92).** The plaintext content of every record is padded with `sodium_pad` to a multiple of a fixed block size before encryption, and unpadded with `sodium_unpad` after authentication; invalid padding fails verification on receipt (section 9.2). The block size is **256 bytes**, fixed in this document because it sets what ciphertext lengths reveal. The empty content of a purged tombstone is not padded, and neither are the fixed-size key wraps (the Vault Key and the Master Key wraps). The encrypted part of Local Config is padded the same way, so its length does not reveal how many peers and devices it lists (D159). Empty content is valid only in a record with `deleted = true`; any other record whose content is empty fails verification on receipt.
- **Record size cap (D129, D139).** The plaintext content of a record, before padding, MUST NOT exceed **1 MiB**, fixed in this document because it bounds what a peer can make a device allocate. An Item's content has a lower **item cap**: 1 MiB minus the fixed overhead of an Item Version of a trashed state, which holds both `itemId` and `trashOperationId` (with their CBOR framing, which `crypto-spec.md` fixes exactly), so every edit, trash, restore from the trash and conflict loser of an item within the item cap fits the record cap (D139, D143). A write above either cap is refused, an imported item above the item cap is skipped, a received record whose ciphertext is longer than the padded cap allows fails verification on receipt (section 9.2) before any decryption, and a received Item or Item Version whose item content, not counting `trashOperationId`, exceeds the item cap fails it after decryption (D144). Changing either cap is a record format change (D32). `sync-protocol.md` defines the message framing that carries records up to this size over a DataChannel.
- The encrypted record format, `.bvault`, the pairing protocol, the sync protocol and cryptographic envelopes MUST be versioned.
- **Record format version (D32).** Each record carries its own `recordFormatVersion` in the cleartext header, bound through the AAD. It is independent of the pairing and sync protocol versions: a protocol version change MUST NOT change the AAD of stored records. Records of an older supported format stay readable and are migrated by re-encryption (D38): migration rewrites only `recordFormatVersion` in the header, keeps `hlc` and every other header field, re-wraps the record key under the new AAD, and creates no Item Version. When two devices hold the same `recordType`, `recordId` and `hlc`, the higher `recordFormatVersion` wins in sync. The Recovery Envelope's Master Key wrap is bound to `recordFormatVersion` and can be rewritten only with the Recovery Phrase, so the envelope migrates only at regeneration or Check Recovery Phrase (never while its metadata holds unknown content, D98), and a record format stays supported as long as any Recovery Envelope may still use it. A record with an unknown `recordFormatVersion` is rejected; a device that does not support a newer format keeps its own copy until it is upgraded. Such a device MUST tell the user to update the app and record in Local Config the `deviceId` of each peer whose records it rejected; while any is recorded, export MUST warn that the backup may be incomplete, and re-founding MUST warn that those records are lost (D116). A peer is removed from that list when a sync with it completes with no record rejected for its format or type, so a sync with a peer that never held those records clears nothing; the user MAY also dismiss the warning with explicit confirmation, for a peer that is lost or retired (D115). A pairing whose joining device does not support a record format or record type that the device holding the vault holds is refused before the handshake (section 8.3, D122). The first full sync of a pairing that still holds any record with an unknown `recordFormatVersion` aborts before the commit, so the joining device's storage stays empty, and tells the user to update the app (D68). A fresh restore or backup merge that holds any record with an unknown `recordFormatVersion` is rejected as a whole, writes nothing, and tells the user that the backup needs a newer app (D61). A record with an unknown `recordType` is handled exactly like one with an unknown `recordFormatVersion` in sync, pairing and restore, since its merge rules are unknown: a device never stores, merges or relays a record type it does not know (D81). An incompatible format MUST NOT be silently interpreted as compatible. Downgrade attacks MUST be considered during version negotiation.

## 6. Data model

Only the minimum metadata needed for synchronization is in cleartext.

**Record header (D18, D21, D32).** Every synchronized record has the same cleartext header: `recordFormatVersion`, `recordType`, `recordId`, `hlc`, `deleted`, `keyEpoch`. The header is the source of the AAD (section 5.6) and of the sync summaries (section 9.2), and every header field is authenticated through the AAD. `vaultId` is not in the header but is bound through the AAD. A record's identity is the pair (`recordType`, `recordId`) in storage, sync summaries and merge (D158): some `recordId`s are public (the Vault Key and Recovery Envelope IDs, `deviceId`), so a record of one type can never replace a record of another type that happens to share its `recordId`.

| Record or local structure | Header specifics | Encrypted content |
| --- | --- | --- |
| Item | `recordId` = item ID | Record key (wrapped); `templateId`, `templateVersion`, title, fields (D165), `folderId` (optional), tags, notes |
| Folder (D14) | `recordId` = folder ID | Record key (wrapped); name, `parentId` (optional), `trashOperationId` (when trashed) |
| Item Version (D6) | `recordId` = `versionId` (deterministic, opaque); `hlc` = the snapshot's `hlc` | Record key (wrapped); `itemId`, full item snapshot |
| Vault Key | `recordId` fixed per `keyEpoch` | Vault Key wrapped by the Master Key's wrapping subkey (D23) |
| Recovery Envelope (D2, D16, D24) | `recordId` fixed per vault; `keyEpoch` = epoch of the Vault Key that wraps its record key | Master Key wrapped by the envelope subkey; record key (wrapped) protecting the metadata: recovery keyslot public key, `phraseId`, phrase creation date |
| Device (D26, D30) | `recordId` = `deviceId` | Record key (wrapped); public identity key (immutable), display name, `retired` flag, `registeredAt` |
| Local Config (not synchronized, D58) | — | **Cleartext part** (what unlock and startup need): its format version (D164), `vaultId` (D25), `localConfigId` (random, generated with this Local Config and bound into every local wrap, D121), local KEK material (salt, parameters, Master Key wrapped by the Device KEK), PRF KEK state, and the `vaultId` of the vault this database replaces, only until that vault's database is deleted (D89, D96). **Encrypted part**, under the Master Key's Local Config subkey: device identity (D67), security preferences (auto-lock and similar), date of the last completed sync with each peer (D34), date of the last backup made on this device, `phraseId` of the last Recovery Envelope seen (D43), `deviceId`s of the Device records seen and of those seen as retired (D47, D48), HLC state, the greatest HLC issued or accepted (D62, D109), `deviceId`s of the peers whose records were rejected for a newer format or an unknown type (D68, D81, D115) |

An Item also carries `trashOperationId` in its encrypted content while trashed. A record in the trash allows only restore from the trash and the automatic purge: an item or folder in the trash is not edited, moved, renamed or retagged until it is restored from the trash, so its purge date never moves (D143). Templates are not records in v1 (D20): factory templates are versioned definitions in code, and an item references one by `templateId` and `templateVersion`. The `Template` record type is reserved for user-created templates after v1.

**Items from a newer app version (D52).** An Item or Item Version can carry content that an older app does not know: a field type, a `templateId`, a `templateVersion` or any other content key. A device that decodes such content MUST show the item read-only and tell the user to update the app, since an edit would drop what it cannot read and then win LWW on every device. Unknown content is never silently ignored, and the record is kept and synchronized as received.

**Folders and Devices from a newer app version (D59).** A Folder or Device record can also carry content keys an older app does not know. Such a record is not read-only: every write keeps the unknown keys and their values unchanged, so renaming, moving, trashing or retiring never drops them and is never blocked. A known key holding an invalid value is not unknown content: the record fails verification (D165).

**Recovery Envelope from a newer app version (D98).** The Recovery Envelope's metadata can also carry content keys an older app does not know. Regeneration builds a new envelope and would drop them, then win LWW on every device, so while the held envelope holds unknown metadata it is read-only: regeneration and its format migration at Check Recovery Phrase are blocked, and the UI tells the user to update the app. Check Recovery Phrase still verifies the phrase and the public key, and the envelope is kept and synchronized as received.

**Local Config (D58).** Only what unlock needs stays in cleartext. Everything else is one encrypted blob under a Master Key `crypto_kdf` subkey, with `AAD = versioned purpose label ‖ vaultId ‖ localConfigId` (section 5.6), so someone holding the locked device can neither read the sync history nor edit the notice state or security preferences. Every device of a vault uses the same subkey, so without `localConfigId` the blob of another device of the vault would authenticate here and bring that device's identity, security preferences, notice state and HLC state; binding `localConfigId` makes it fail, and changing `localConfigId` to the other device's breaks this device's own Master Key wraps (D121). **Residual risk:** the blob can be rolled back to an earlier copy of itself. This only shows notices again or restores a setting the user chose before, and the HLC state is protected by D62.

**Read-only records (D39, D52).** An Item, Item Version or Recovery Envelope is read-only while it holds content from a newer app version (D52, D98); a Folder or Device record never is for that reason (D59). Any record is read-only while its HLC is beyond the future-clock bound (section 9.2, D74). A read-only record allows no edit, move, trash or restore from the trash; the automatic purge still runs (D94). The future-clock rule applies to every record type (D74): renaming a Device record or regenerating the Recovery Phrase is blocked while the held Device record or Recovery Envelope is beyond the bound, since the new write would lose LWW to the held record once peers accept it. Retirement stays allowed, because a retired Device record wins whatever its `hlc` (D31). The whole vault is also read-only, purge and retirement excepted, while its HLC state is beyond the future-clock bound of the device clock (section 9.2, D73, D85). An action that would write a read-only record is blocked as a whole, never applied in part. Trashing a folder whose subtree holds a read-only record is refused, and the UI lists those records and why each is read-only. Re-founding is the one exception (D60): it creates a new vault, so it carries each such item's decoded content over unchanged, unknown keys included, and gives it a fresh HLC.

Folders and tags MUST remain encrypted, including the folder tree structure (`parentId`), so synchronization metadata does not expose how the user organizes the vault.

**Folders (D14).** Folders nest with unlimited depth.

- An item belongs to **exactly one** folder or to the vault root (no `folderId`). It never appears in more than one place. Tags remain flat and are the way to classify items across folders.
- Moving a folder edits its `parentId`; moving an item edits its `folderId` and creates an Item Version like any other edit.
- Siblings are sorted alphabetically. There is no manual ordering in v1.
- Deleting a folder sends it, its subfolders and their items to the trash (refused if any of them is read-only, D52), each with its own tombstone, and records the same random `trashOperationId` in every record trashed by that action. Restoring the folder from the trash restores exactly the records carrying that `trashOperationId`; an item trashed earlier by a separate action stays in the trash. A subfolder restored on its own brings back only the records of that operation inside it (D171). An item or folder restored from the trash while its parent folder is in the trash, whichever trash operation trashed it, is moved to the vault root (its `folderId` or `parentId` removed), so it never moves again without a user action (D106, D112).
- Folders have no version history. Concurrent edits to the same folder (for example, rename on one device and move on another) are resolved by LWW and one of them is lost; this limitation is documented.
- The tree is **derived at read time** with deterministic rules, so every device shows the same tree without writing anything (see section 9.3).

**Single vault in v1 (D13, D79).** In v1 each installation holds exactly one vault. Folders and tags are the way to organize items. `vaultId` is kept in AAD, because it prevents mixing records from different vaults during restore, merge or pairing. Multiple vaults per installation come after v1 (section 20); so that they need no storage migration, v1 already names its IndexedDB database and its Web Lock by `vaultId`, and keeps Local Config inside that database (D79, D82).

**Field types (v1):** text, long text, secret, URL, email, phone, date, number, TOTP (codes computed as in D127), seed phrase (a wallet's BIP39 phrase, unrelated to the Recovery Phrase). The list is closed in v1; the Crypto Wallet template combines these types (D100). Attachments come after v1.

**Factory templates:** Login, Secure Note, Card, Identity, Developer Credential, Crypto Wallet, Document. Templates are data definitions, not separate security models. A template sets an item's initial fields; an item can also hold fields beyond its template, each of a v1 field type, and import relies on this (D124).

**Item content (D165).** An item's fields are an ordered list; each field has a field type, a value, an optional field role (its meaning in the item's template, such as username or password) and an optional label, and a field with no label is shown with its role's localized name. Templates only set an item's initial fields: items are never migrated to a newer `templateVersion`, a role never changes meaning within a template, and an item's template cannot be changed in v1. An item holds content from a newer app version (D52) when it has an unknown key, field type, role, `templateId` or `templateVersion`, or a known value that fails its validation; so a later app that relaxes a rule on a known value uses a new key or field type instead. Saving an item whose content is unchanged writes nothing, so it issues no HLC and stores no Item Version. `record-content.md` fixes the content of every record and of Local Config.

## 7. Local storage and locking

- IndexedDB stores only already-encrypted records and Local Config, in one database per vault named `blindvault-<vaultId>`. Local Config has its own object store in that database, so records and Local Config are written in one transaction (D33, D62, D82). At startup the app finds the vault's database by listing databases (`indexedDB.databases()`) with that name prefix; no pointer to it is kept anywhere else. **A database is a vault only once its Local Config is committed (D89).** Creating a database and its object stores runs in its own `versionchange` transaction, and IndexedDB transactions cannot span databases, so at startup the app deletes every `blindvault-` database that holds no committed Local Config. An operation that replaces the vault with one of a different `vaultId` (re-founding, restoring a different vault, replace by pairing with a different vault, D150) writes the new database in full, with its Local Config recording, in its cleartext part, the `vaultId` it replaces, and deletes the old database only after that commit, then clears that value (D96); if startup finds a complete database that replaces another complete one, it deletes the replaced one. The old vault therefore stays intact until the new one commits. An operation that replaces the vault with one of the same `vaultId` (replace by pairing, or a fresh restore over a vault this device holds, D153) cannot build a second database under the same name: it commits in one transaction in the existing database that clears its records and Local Config and writes the new ones, so the old vault likewise stays intact until that commit. `localStorage` stores only non-sensitive UI preferences (theme, language, layout) and the STUN list (D209). Security preferences such as auto-lock live in Local Config.
- **One active app window (D51).** Every app window (a tab or window of the app) on a device shares IndexedDB and one `deviceId`, so two app windows writing at once could produce two different writes with the same HLC, which D19 rules out. Only the app window holding an exclusive Web Lock (`navigator.locks`), named by `vaultId` (D79), opens the vault; an app window that cannot acquire it MUST NOT open the vault, shows that BlindVault is open in another window, and offers to take over. Taking over locks the vault in the app window that held it, which ends its sync session.
- **Installation guard (D97, D108).** The vault's Web Lock exists only once a `vaultId` is known, so it cannot guard a database that is still being built. Every app window therefore holds the installation guard, an exclusive installation-wide Web Lock named `blindvault-installation`, while it runs the startup cleanup (D89), creates a vault, pairs, restores, re-founds or erases, until that operation commits or aborts. An app window that cannot acquire it MUST NOT create, replace or delete any `blindvault-` database, and shows that BlindVault is busy in another window. Otherwise a second app window's startup cleanup could delete a database another app window is still building, or two app windows in onboarding could each create a vault. **Removing a vault (D154).** Erase, replacing the vault (by pairing or restore) and re-founding also hold the Web Lock of the vault they remove, taking it over if another app window holds it, which locks the vault there; they acquire it before the installation guard, so two app windows never wait on each other. The startup cleanup requests a replaced vault's Web Lock without waiting (`ifAvailable`) before deleting its database, and skips the deletion while another app window holds it. Erase and replacement run without unlocking, so without this rule an app window could remove a vault that another app window holds unlocked.
- **Storage belongs to the origin (D90).** IndexedDB, Web Locks and WebAuthn credentials are bound to the app's origin. Moving the app to another origin (a new domain, or self-hosting) leaves the vault behind: the user makes a backup and runs a fresh restore at the new origin, or pairs a device there, and sets up WebAuthn unlock again.
- Call `navigator.storage.persist()` when a vault is created, paired or restored on the device, show the persistence status, and monitor `navigator.storage.estimate()`. Settings shows both in its "This device" section and, while storage is not kept, offers to ask again on the user's click only; the app reads them at unlock, on every return to visible and after each request, never by polling (D196).
- Browser storage eviction is a data-availability risk. The application MUST NOT imply that browser storage is permanent.
- If persistence is denied and there is only one device, show a persistent warning recommending a backup and pairing. A device is the only one when the vault holds no non-retired Device record other than its own, whether or not it is registered (D119).
- **Safari (D55).** WebKit deletes the script-writable storage of a site (IndexedDB and service-worker caches included) after seven days of Safari use without user interaction on it, while an installed app has its own counter of days of use and is not expected to lose its own data; Safari grants persistent storage by heuristics such as running as an installed app. This rule rests on WebKit's documentation, not on a measurement over days, since no measured result could relax it (D160). On Safari the UI MUST recommend installing the app (Home Screen on iOS, Dock on macOS) and show a stronger persistent warning while the vault runs in a plain tab. **The installed app is a separate installation (D103):** it does not share storage with the Safari tab (measured on iOS and macOS, D160), so on Safari onboarding recommends installing *before* creating, pairing or restoring. A vault already in a tab moves to the installed app, then the tab is erased and its Device record retired; the UI MUST NOT imply that installing the app carries the vault over. On macOS and iPadOS, where both can run side by side, the installed app pairs with the tab (copy/paste on the same device). On iPhone only one of them runs in the foreground and iOS suspends the other, so the pairing handshake and first full sync cannot complete: the tab exports a backup and the installed app runs a fresh restore of it, becoming an unregistered device that gets its own Device record at its next pairing or re-admission (D110). The Phase 0 storage spike tried same-device pairing on iPhone and could not complete it, so D110 stands.
- **Erase** removes the vault and the Local Config from the device, leaving it with no vault. Before erasing, the UI MUST warn that changes existing only on this device are lost and recommend a backup. The confirmation names this device's Device record and tells the user to retire it from another device afterward, since a device cannot retire its own record (D41); while the vault is locked it cannot name it, and says so (D183); until then the other devices keep offering it as a sync peer. On an unregistered device the confirmation states instead that there is no Device record to retire. Erase is offered in Settings while unlocked and on the unlock screen while locked, asks for no password, since a locked vault can be erased without one, and needs the user to check "I understand that the vault on this device will be erased"; on the only device (D119) the warning says the vault is lost for good without a backup. Erase locks the vault first, then deletes its database under its Web Lock and the installation guard (D97, D154), and ends on the start screen, which says the vault was erased and repeats the retirement advice (D205).
- **Search (D132).** Search runs only over decrypted state in memory. It reads titles, tags, folder names, notes and the values of non-secret fields; it never reads `secret`, TOTP or seed-phrase values, so the index holds no secret and typing a guessed password into search confirms nothing. No search index or other plaintext derived from items is persisted, in IndexedDB, `localStorage` or anywhere else, and the in-memory index is cleared on lock.
- **On lock:** remove plaintext items from state, release keys, clear caches, and block cryptographic operations. Auto-lock after inactivity is configurable from 1 to 60 minutes, 5 minutes by default (D88, D151). The app also locks after being hidden (`visibilitychange`) for a configurable time, independently of the inactivity timer: 1 minute by default, configurable from immediately to 15 minutes (D54, D151). Neither can be turned off; the ranges are fixed in this document because they bound how long an unattended device stays unlocked (D151). A lock of any kind aborts every operation in progress and discards its in-memory state: a pending reconnection exchange, a sync session, a pairing or re-admission on either device (section 8.4), and a re-founding before its commit (D93). Nothing is exempt from locking (only the inactivity timer pauses while a Recovery Phrase is shown, below); when an exchange requires leaving the app, such as copy/paste mode on a phone, the UI states that staying away longer than the hidden-app lock time cancels it. Vault creation, a fresh restore and an import follow the same lock rules before their commit and are aborted, with nothing persisted, by a lock of any kind (D104, D125). **Recovery Phrase display (D104).** The inactivity timer is paused while a Recovery Phrase is shown or being confirmed (creation, regeneration, re-founding), since writing down 24 words can take longer than the auto-lock time; the hidden-app lock still applies. **System UI (D105).** A file picker, a WebAuthn prompt or a permission prompt may report the app as hidden on some platforms; this is not an exemption either, so with the hidden-app lock set to immediately, an export, a backup merge or a WebAuthn setup may lock and must be repeated, and the UI says so when that setting is chosen. The Phase 0 storage spike records which system UIs report the app as hidden. Memory zeroization in JS is not guaranteed, and this MUST be documented.

## 8. Identity and pairing

Pairing is one of the most security-sensitive protocols in BlindVault. It MUST be implemented as a formally specified protocol (`pairing-protocol.md`), not an informal WebRTC exchange.

### 8.1 Identity

Each device has an X25519 key pair, which is the device's **Noise static key**. The private key is local, encrypted at rest inside the encrypted part of Local Config (D58, D67), and MUST NOT be synchronized. The public key is synchronized in the Device record. Device identity MUST be authenticated during synchronization.

`deviceId = BLAKE2b-128(static public key)` (D19). It is derived, so a device cannot claim another device's ID with a different key.

### 8.2 Handshake (D1)

- Suite: `Noise_*_25519_ChaChaPoly_BLAKE2b`, an existing implementation on top of libsodium, validated against the official test vectors.
- **Pairing:** `Noise_XX`. **Synchronization:** `Noise_KK`, since both sides already know each other's static key.
- Prologue = versioned protocol label ‖ hash of the initiator's pairing payload ‖ hash of the responder's pairing payload ‖ DTLS fingerprints of both sides, in fixed role order (initiator first). Both pairing payloads are bound, not only the first. The transcript MUST include all security-relevant negotiation values, with a canonical, versioned encoding.
- The SAS is derived from the final handshake hash. It MUST bind both peers and the session, MUST prevent replay across sessions, and MUST be displayed on both devices and explicitly confirmed by the user on both devices (D148): the side holding the vault transfers the Master Key only after its own confirmation and an authenticated confirmation message from the joining device, the joining device rejects a Master Key that arrives before its own confirmation, and in re-admission neither side sends its key-confirmation MAC before both have confirmed. SAS length and brute-force analysis, including the initiator's commitment, which every pairing carries in QR and copy/paste modes alike (D199), are defined in `pairing-protocol.md`.
- WebRTC DTLS is transport only and MUST NOT be the trust mechanism. A device MUST NOT be trusted merely because a WebRTC connection succeeded.

### 8.3 Pairing payload and QR (D4)

- Binary pairing payload with version, session ID, DTLS fingerprint (32 bytes), ICE ufrag, ICE pwd, candidates (host and srflx; a host candidate may be an mDNS `.local` name instead of an IP address, D136) and capabilities. Noise keys are not in the payload: ephemeral and static keys travel only in the `Noise_XX` handshake messages. The initiator's payload adds a commitment, in QR and copy/paste modes alike (D199), defined in `pairing-protocol.md`. Encoded in base45 (QR alphanumeric mode). The original spec estimated about 200–300 bytes; the Phase 0 pairing spike measured at most 125 bytes (QR version 8).
- The receiver rebuilds the SDP from the payload. ICE gathering completes before the QR is generated, with no trickle.
- **mDNS host candidates (D136, D161).** Browsers may replace a host candidate's IP address with a random mDNS name (`<uuid>.local`) while the page holds no camera or microphone permission. Pairing and reconnection payloads encode an mDNS name's UUID in 16 bytes. The Phase 0 pairing spike found that Safari on iOS does this until the camera is granted, while Chrome on Android sent raw IP host candidates with no capture permission. In QR pairing the scanning side holds the camera before gathering, so it always sends a raw IP host candidate, and same-network pairing does not depend on resolving an mDNS name. Same-network connections where neither side holds a capture permission (copy/paste pairing, reconnections) may carry only mDNS names and then depend on the local network resolving mDNS; that case is measured in Phase 5, with the manual sync flow (D212).
- Bidirectional exchange: A shows its QR and B scans it, then B shows its response and A scans it. Copy/paste is the fallback for desktops without a camera: each payload screen shows the QR code and the text together, and each screen that takes a payload offers the camera beside a paste field; a scanned text goes through the same parser as a pasted one (D208). Between two physical devices it MAY go through any channel, such as a messaging app or email to oneself, since authentication never depends on the channel (SAS and commitment in pairing, `Noise_K` and `Noise_KK` in reconnection). For a pairing payload the UI states that whoever sees the code, or the channel that carries the text, sees the device's network addresses (D208); a reconnection payload is encrypted to the peer (section 9.1), so the channel sees only that an opaque payload was sent (D117).
- Animated QR MUST NOT be implemented without real-world evidence that a static QR is insufficient.
- **Admission flow (D50).** Pairing and re-admission are the two admission flows; both use the same `Noise_XX` handshake and SAS confirmation. The capabilities include a "holds a vault" flag, bound through the prologue like the rest of the payload. If one side holds a vault, the flow is pairing and that side transfers the Master Key; if both do, it is re-admission; if neither does, both abort. The flag reveals no vault data.
- **Supported formats (D122).** The capabilities also list the record format versions and record types the app supports. In pairing, the side holding the vault reads the joining side's payload before the handshake and refuses the pairing, with no handshake, no Master Key transfer and no Device record, when that list lacks a `recordFormatVersion` or `recordType` it holds; the UI tells the user to update the app on the joining device. The abort of the first full sync (D68) remains as the backstop. The list reveals only the app version range.
- The pairing payload MUST NOT contain vault data.

### 8.4 Flow

```
A asks again for its local password or a passkey assertion and opens the Master Key for this pairing only (D202)
B generates its identity, creates the local password and derives the Device KEK (all in memory only)
→ A's QR → B's QR → WebRTC/DTLS → Noise_XX handshake → SAS on both devices
→ confirmation on both devices (D148) → Master Key and vaultId transferred over the Noise channel
→ B acknowledges receipt and sends its display name
→ A writes B's Device record (static key seen in the handshake, B's display name)
→ first full sync over the same channel (sync protocol, no new exchange); B keeps the received records in memory
→ B wraps the Master Key, encrypts its Local Config (identity included), and persists the records and Local Config in one storage transaction (D33)
→ B records the completed sync with A in that transaction and sends a commit acknowledgement; A records the completed sync with B (D34)
→ B is a registered device → optional WebAuthn setup
```

`Noise_XX` transmits both static keys during the handshake, so B's identity MUST exist before it. B holds the identity, the Device KEK and the Master Key only in memory until the commit, and discards them if pairing aborts. A lock, auto-lock or hidden-app lock on either device aborts the pairing (D93).

A writes B's Device record only after B acknowledges receiving the Master Key, bound to the static key A authenticated in the handshake, so B cannot choose its key at registration; the key is immutable afterwards (D26). Every device MUST reject a Device record whose `recordId` is not `BLAKE2b-128` of its public key, or whose public key differs from the one already stored for that `recordId`. Only the display name and the `retired` flag can change, and `retired` only from false to true (D30, D31). Any unlocked device can rename any Device record, its own included, by LWW, unless the held record is read-only (D74, D118). Device records cannot be deleted in v1, so a pairing interrupted after the record was written leaves it in place.

**Last sync per peer (D34).** No synchronized record says whether a device has ever synced. Each device keeps, in Local Config, the date of its last completed sync with each peer, and the UI shows it next to the Device record's `registeredAt` ("last synced with this device: never" or a date). In pairing, B records its sync with A in its commit transaction, and A records the sync only when it receives B's commit acknowledgement.

**Who creates Device records (D30, D35, D40).** The vault creator creates its own Device record at vault creation; a re-founding device is the creator of the new vault and does the same (D40). Every other Device record is created after SAS confirmation, in pairing or re-admission, by a device that holds the vault: in pairing, A writes B's record and, if A is an unregistered device (section 10), its own as well, since both static keys were authenticated in the confirmed handshake. In re-admission, a record is written only for a device whose Device record neither side holds: the other side writes it, or the initiator writes both if neither device has one. Records already held by either side reach the other through the merge sync (D49). No device creates a Device record in any other situation; the only later changes to one are its display name and its `retired` flag (D26, D31).

**Retired devices (D30, D31, D41).** Any device holding the unlocked vault, registered or not, can mark any Device record other than its own as retired, for a device that was lost, erased or never finished pairing. Retirement hides the device in the UI, removes it from recovery recommendations, and blocks it from syncing: a device ends a sync session as soon as `Noise_KK` authenticates a peer whose Device record is retired, before any summary is exchanged. Before closing, it sends that peer its own retired Device record, the only record it sends, so the retired device learns of its retirement (D45); the receiver validates it like any Device record (D26). The same holds during an open sync session (D69): when the peer's Device record becomes retired, through a local retirement or a record pushed in the session, the device sends that peer its retired Device record and ends the session at once. A device that receives its own Device record as retired during a session ends the session and shows the own-retirement notice. Retirement asks for an explicit confirmation, not for the local password, and records the retired device as seen-as-retired in the same commit (D186).

Retirement is **irreversible**. The HLC's `deviceId` is not authenticated as the writer, so any holder of the Master Key, including the retired device, can forge a write that appears to come from another device; a reversible flag could therefore be undone through a peer that has not yet received the retirement. Instead, a Device record with `retired = true` is never replaced by one with `retired = false`, whatever their HLCs; among records with the same `retired` value, LWW applies as usual. Every device converges on the retirement, and no write can undo it. A device retired by mistake must be replaced by pairing (D150, D153), getting a new identity. The UI MUST ask for confirmation stating that retirement cannot be undone.

Retirement is not revocation (section 20). The retired device keeps everything it already had and still holds the Master Key, and until the retirement reaches a peer it can still sync with that peer. Because it holds the Vault Key, it can also write a valid Device record for a new identity; once that record reaches any peer, through one that has not received the retirement or through a backup the user merges, it spreads by sync and the device syncs again under the new identity. Retirement therefore stops an honest or unmodified device, not a malicious holder of the Master Key; the new-device notice (D48) makes such a record visible. A retirement also does not block backups: a backup carries no proof of which device made it, so a backup made by the retired device can still be merged by the user (D41). The UI MUST say so, and MUST point to re-founding (D28) when the device may be in someone else's hands.

**Own retirement (D41, D45).** A device that receives its own Device record with `retired = true` MUST show a persistent notice that it was retired and must be replaced by pairing to sync (D153), and that if the user did not retire it, someone holding the Master Key did, which calls for re-founding (D28, D47). It MUST stop offering sync, re-admission and the pairing of another device; it can still join a pairing as the joining device, which replaces its vault (D153). Its local vault stays usable, including making backups and re-founding (D47).

**Retirement notice (D47).** A device that receives, through sync or backup merge, another device's Device record turned retired, which it had already seen but not yet seen as retired, MUST show a one-time notice naming that device. A Device record it had never seen that arrives already retired triggers no retirement notice: it appears in the new-device notice, marked as already retired (D53). A Master Key holder can retire every other device through a lagging peer, and retirement cannot be undone; the notice makes such a retirement visible.

**New-device notice (D48).** A device that receives, through sync, re-admission or backup merge, Device records it has never seen MUST show one notice listing them, stating that a device the user did not pair means a Master Key compromise (section 14). Records it wrote itself do not trigger it, and the notice is suppressed when the device held no Device record before (the first sync of a pairing, or a fresh restore); in that case the device records every received `deviceId` as seen, and every retired one as seen as retired, without any notice (D53). The `deviceId`s seen, and those seen as retired, are kept in Local Config.

**Retired peer in pairing (D45).** A device may not yet know it was retired. The joining device in a pairing MUST abort before its commit if the first full sync shows the peer's own Device record as retired, so its storage stays empty (D33). In re-admission, each side MUST abort as soon as the Device records it holds or receives show the peer's own Device record as retired (D49). Otherwise the joining device would be registered only on a retired device, which no other device syncs with.

**Interrupted pairing (D33).** B persists nothing before the single commit transaction, so an interruption at any earlier step, including a failed first sync, leaves B's storage empty and the user pairs again. If A wrote B's Device record but never received the commit acknowledgement, A shows the pairing as not completed and offers to mark that record retired. Because retirement cannot be undone, the offer MUST first ask the user to check B: if B shows the vault as ready, the commit succeeded and the user syncs with B instead (D41). If the commit succeeded but the acknowledgement was lost, B is a registered device and A updates its last-sync date at their next sync.

A mismatched SAS MUST abort. No key or recovery secret is transferred before confirmation, and the transfer MUST occur inside the authenticated Noise channel.

The joining device MUST have no vault (D13), except for re-admission (below, D50) and replace by pairing.

**Replace by pairing (D150, D153).** A device already holding a vault, the same one or a different one, can join a pairing that replaces it. It sends `holds a vault = false`, so the flow is pairing, not re-admission. The user confirms the replacement as for erase (section 7), without unlocking the old vault, since replace by pairing is also the path for a forgotten local password, an own retirement, a clock set far ahead and a cloned installation: the confirmation recommends a backup, names the old vault's Device record, or says its name cannot be shown while the vault is locked (D183), and tells the user to retire it from another device of that vault. The joining device holds the old vault's Web Lock throughout (D154). It learns the received `vaultId` only with the Master Key and compares it with the one in its cleartext Local Config: a different vault replaces the old one as a restore of a different vault does (D89, D96), deleting the old database only after the new one commits; the same vault is committed in one transaction in the existing database (section 7, D153). Either way a failed pairing leaves the old vault intact. The old vault's passkey is handled as after erase (D120). It starts only from the unlock screen, as a replacement by a restore does, and the user confirms it at the joining device's password step, before any connection (D204).

**Read-only vault (D102).** Pairing and re-admission write Device records, which need a new HLC, so a device whose vault is read-only because its clock went back (section 9.2, D73) does not offer either; the UI states when they become available.

**Re-admission (D22, D29, D49).** Two devices holding the same vault, where either lacks the other's Device record, run the same `Noise_XX` admission handshake with SAS confirmation. Typically one is an unregistered device restored from a `.bvault`; it can also be two registered devices whose pairing device was lost before they synced with it. After confirmation, each side sends a key-confirmation MAC inside the Noise channel: BLAKE2b keyed by the Master Key's re-admission subkey (D23) over its role label (initiator or responder) and the final handshake hash. Each side verifies the other's MAC; a mismatch aborts the re-admission, and the UI states that the devices hold different vaults and offers to replace one of them by pairing (D50, D153). This proves both devices hold the same Master Key, bound to this session, and reveals nothing when they do not. Comparing `vaultId` is not enough, because `vaultId` is not secret. The Device records are then written as described above (D35, D49), and the two devices run a full merge sync; no Master Key is transferred, since both already hold it. This keeps one admission rule: a device joins the set of synchronizing devices only through admission, that is, SAS confirmation.

## 9. Synchronization

QR + WebRTC synchronization avoids any permanent synchronization infrastructure. Sync requires the vault to be unlocked on both devices, because the Noise static private key is stored only in the encrypted part of Local Config, under a Master Key subkey (D67).

### 9.1 Session establishment (D12)

A browser cannot discover peers or accept inbound connections, so every WebRTC session needs a fresh exchange of connection data (SDP and ICE candidates) through some out-of-band channel. In v1 there is no automatic background sync between devices.

- **v1: manual sync.** The user starts a sync on two devices and exchanges a **reconnection payload** by QR (or copy/paste), in both directions. It is smaller than the pairing payload because identities are already known: no SAS and no new Device record, authentication comes from `Noise_KK` (CRYPTO-INV-008). The `Noise_KK` prologue is the versioned protocol label ‖ hash of the initiator's reconnection payload ‖ hash of the responder's reconnection payload ‖ DTLS fingerprints of both sides, in fixed role order, mirroring pairing (D17). A peer MUST prove possession of the private key for its registered identity, bound to the current session; replaying an old authentication exchange MUST NOT authenticate a device. The user picks the peer in Settings › Devices on both devices and chooses on each whether it shows its code first; each code is shown and read as in pairing (D208), and the channel sees only that an opaque code was sent (D216). Once the DataChannel is open, the two devices run `Noise_KK` and send nothing else before it completes; a peer that fails it is reported as not verified (D217). Every later message travels in the Noise channel, and either side ends the session with `abort` and its reason, which the other device shows (D218).
- **Known peers only.** `Noise_K` and `Noise_KK` need each side to hold the other's Device record. A device that has not yet received a peer's Device record cannot sync with it: if A pairs C, B can sync with C only after B has synced with A (or another device holding C's record). This follows from the admission rule (CRYPTO-INV-007) and is a documented limitation. The UI offers as sync peers only the non-retired devices whose Device records it holds, and only on a device that holds its own Device record; it offers a retired one only to tell it that it is retired, a session that sends it only its retired record (D219): an unregistered device offers no sync, since no peer knows its identity, and offers re-admission and pairing instead (D113). Pairing from an unregistered device is allowed whether or not other non-retired Device records exist; when they do, the UI recommends re-admission and states that those devices can sync with the two paired devices only after re-admission (D141). The UI tells the user to sync first with the device that paired a new one; if that device is unreachable, the two devices run re-admission (D49).
- **Sync session.** While a DataChannel is open, changes made on either device are pushed immediately, until either side closes the session or locks the vault.
- **Transport-agnostic payload.** The reconnection payload is defined independently of how it is delivered (QR, copy/paste through any channel (D117), or a future relay), so a relay added later needs no protocol change. It is encrypted to the peer with the one-way pattern `Noise_K` (both static keys known, sender authenticated), same suite as D1 (D17). No ad-hoc construction such as `crypto_box_seal` on the Noise static key is used. `Noise_K` gives no replay protection; that comes from the `Noise_KK` session that follows. The payload carries no identity in the clear: the user picks the peer on both devices, and the receiver opens the payload with that peer's key (D213). `packages/sync` carries it through a delivery interface, the manual delivery in v1, which a mailbox implements later; a refused payload is reported and the wait goes on, and the pairing payload never goes through a delivery (D215). Details are in `sync-protocol.md`.
- **After v1: optional signaling relay.** Devices drop encrypted reconnection payloads for each other in a mailbox, enabling automatic sync when both are online. The plan:
    - `packages/sync` defines a minimal **mailbox interface**: publish a blob to a topic, subscribe to a topic. Everything above it (payload format, `Noise_KK`) stays unchanged.
    - **First adapter: Nostr**, used directly (not through Trystero). Payloads are published as ephemeral events, which relays do not store, to several relays at once for redundancy. No account is needed and relays can be self-hosted.
    - **Second adapter: ntfy**, for users who want the simplest self-hosted option.
    - The project MUST NOT operate an official relay instance, keeping static hosting as the only operational infrastructure.
    - Off by default. Relays are configured by the user. The topic is derived from a vault secret so outsiders cannot find the user's devices.
    - Relays see only opaque blobs, timing and IP addresses, the same trust level as STUN, and never vault data. Authentication still comes only from `Noise_KK`; a malicious relay can at most disrupt connectivity.
    - Libraries that also manage WebRTC connections (Trystero, PeerJS) are not used, because BlindVault manages its own connections.
- **Limitation of any relay:** "automatic" means syncing whenever BlindVault is open on both devices at the same time. Browsers do not allow WebRTC in service workers and PWAs cannot run reliably in the background, especially on iOS, so there is no sync while the app is closed.

### 9.2 Sync flow

```
connect → Noise_KK (proves possession of the registered identity, bound to the session)
→ if the peer's Device record is retired, send it that record and end the session (D31, D45)
→ exchange summaries (recordFormatVersion, recordType, recordId, hlc, deleted, keyEpoch)
→ transfer divergent records (always encrypted) → merge → persist → ack
```

- **Transfer:** only records that differ SHOULD be transferred. Transferred contents always remain encrypted.
- **Verification on receipt (D57, D64, D66):** before a received record takes part in merge or is persisted, in sync, a backup merge or a fresh restore, the device MUST unwrap its record key with the Vault Key of its `keyEpoch` under the record's AAD and authenticate its content (the empty-content tag for a purged tombstone) and check its padding (D92), rejecting empty content in a record with `deleted = false` and, before decrypting, ciphertext longer than the record size cap allows (D129) and, after decrypting, an Item or Item Version whose item content, not counting `trashOperationId`, exceeds the item cap (D144); for the Vault Key and the Recovery Envelope, the parts the device can open without the phrase. It MUST also recompute every derived `recordId`: an Item Version's `versionId` from its decrypted `itemId` and its `hlc`, the Vault Key record's from its `keyEpoch`, the Recovery Envelope's for the vault, and a Device record's from its public key (D26); a mismatch fails verification (D66). In sync a failing record is rejected, never merged, and the session reports it; a restore holding one is rejected as a whole (D64). Otherwise a faulty peer could send unreadable ciphertext under a newer `hlc` that wins LWW on every device.
- **Conflicts:** last-write-wins per item, ordered by HLC, for simple deterministic v1 conflict handling. The losing version MUST go to history, subject to the history cap (D6): a loser whose `(hlc, versionId)` falls below the cut is dropped. When the dropped state was written by this device (its `hlc` carries this device's `deviceId`), the device MUST show the user a one-time notice naming the item, so no local edit is lost silently. A dropped state written by another device triggers no notice: LWW carries no causal information, so this device cannot tell a concurrent edit from ordinary pruning, and the writing device notifies when it drops its own state (D70). A losing tombstone is stored as an Item Version of its content, with `deleted = false` and the tombstone's `hlc`, since that content can be an edit kept nowhere else; a purged tombstone has no content and adds no version (D56). Folder conflicts lose the older write (section 6). The exceptions to plain LWW are: a retired Device record always beats a non-retired one (D31); the Vault Key record and the Recovery Envelope are immutable per epoch and per `phraseId` (D42, D44, below); and with equal `recordType`, `recordId` and `hlc`, the higher `recordFormatVersion` wins (D38). **Residual risk:** two records with the same `recordType`, `recordId`, `hlc` and `recordFormatVersion` but different content, which a bug, a Master Key holder or a cloned installation (D87) can produce, have identical summaries and never converge; this is accepted. Local purge produces the same situation on purpose, a purged and an unpurged copy of one tombstone, and every device purges on its own (Trash, below).
- **Vault Key, Recovery Envelope and Device records (D42):** these records are never deleted, and a device MUST reject any received with `deleted = true`. The Vault Key record of an epoch is immutable: once a device holds it, the device MUST reject any other version of it, except a format migration (D38) with the same `hlc` that unwraps to the same Vault Key. The Recovery Envelope is immutable per `phraseId` (D44): a device MUST reject a received envelope with the same `phraseId` as the one it holds unless it has the same `hlc` and the same metadata (recovery keyslot public key, `phraseId`, creation date), which only a format migration produces. A legitimate replacement is a regeneration and always carries a new `phraseId`, which triggers the D43 notice. This keeps a retired or faulty device holding the Master Key from making the vault unreadable through LWW, or from silently replacing the envelope so that the Recovery Phrase no longer opens new backups. **Residual risk:** the envelope's Master Key wrap cannot be verified without the phrase, so a forged migration (same `hlc` and metadata, a higher supported `recordFormatVersion`, junk wrap) would be accepted. This is possible only once a second record format exists, and a future format migration design MUST address it.
- **HLC (D19):** `(physicalMs, counter, deviceId)`, compared lexicographically, so two records never tie. Monotonic per device: the device's HLC state, the greatest HLC it has issued or accepted (receive rule, below), is kept in Local Config and written in the same storage transaction as each write or accepted record, and on startup the clock resumes from the greater of that value and the greatest `hlc` held, within the cap below (D62). If the HLC state is itself beyond the cap, the device clock went back (set by the user or corrected by the OS): the device MUST NOT issue an HLC that is not greater than every one it issued before, so the whole vault is read-only, purge and retirement excepted, until the physical clock brings that HLC within the bound; the device still receives records in sync, and the UI states that the device clock went back and when writing resumes (D73). When writing would resume more than the future-clock bound later, as after a clock set far ahead and then corrected, the UI also offers to replace the vault by pairing with another device (D153), when one exists, or to re-found, and states that the changes made with the wrong clock exist only on this device, since peers rejected them, and stay readable so their values can be copied by hand (D149). Pairing and re-admission are not offered in that state (D102). Re-founding stays available: it creates a new device identity, whose HLC starts from the physical clock. A retirement in that state takes the HLC state with its counter incremented, the only HLC a device issues beyond the cap: it stays monotonic, a retired Device record wins whatever its `hlc` (D31), and a peer whose bound it exceeds accepts it once its clock catches up (D85). **Receive rule (D109).** When a record is accepted in sync or a backup merge, the HLC state advances to the greater of itself and the record's `hlc`; every write takes an HLC greater than the HLC state and greater than the `hlc` of the record it replaces. Otherwise an edit made after receiving a record from a device with a faster clock would lose LWW to the state it edits. A record accepted read-only beyond the bound (below) does not advance the HLC state past the cap. The HLC has a canonical fixed-length serialization, and a future-clock bound keeps malformed HLCs from gaining unbounded future dominance. The bound is **24 hours** (D76): an HLC whose physical time is more than 24 hours ahead of the receiving device's physical clock is beyond it. In sync, a record whose HLC is beyond the bound is rejected, never normalized, and the UI warns; it is accepted once the receiver's clock brings it within the bound. A backup merge holding such a record is rejected as a whole, and the UI says when it can be retried (D64). A fresh restore and the first full sync of a pairing, on the joining device, are the exceptions (D37, D39, D101): they accept every record, since an empty device holds nothing that such a record could override. The HLC state is never advanced beyond the physical clock plus the bound, including after a fresh restore, so this device's own writes are acceptable to any peer whose clock is not behind this device's; a peer whose clock is behind rejects them only until its clock catches up. A record received in a fresh restore or a pairing's first full sync whose HLC is beyond the bound is read-only until the clock brings it within the bound: no edit, move, trash or restore from the trash, since any such write would lose LWW to the record itself. Purge is not blocked, because it does not change the header. The UI shows when the record becomes editable, and peers reject it in sync until then.
- **Tombstones (D27):** a tombstone is a record with `deleted = true`. Until purge it keeps its encrypted content, so it can be restored from the trash. After purge only the header, the wrapped record key and an AEAD tag over empty content remain, so it stays authenticated (D21). Tombstones are synchronized and kept indefinitely in v1, so a stale offline device cannot resurrect deleted content. A tombstone beats an older edit. A newer write with `deleted = false`, such as a restore from the trash, beats the tombstone. Tombstones MUST NOT be removed merely because the local device has not seen the item recently. A future version MAY compact tombstones once device membership and acknowledgment state prove that all known devices have observed them.
- **History (D6):** Item Versions are synchronized records. Every edit of an item, including a move, a trash or a restore from the trash, stores the item's state before the edit as an Item Version with that state's `hlc`; a conflict loser is stored the same way. `versionId = BLAKE2b-keyed(version-ID subkey, itemId ‖ hlc)`, where the version-ID subkey is a `crypto_kdf` subkey of the Master Key with its own context. It is deterministic, so when two devices each store the same conflict loser they produce the same record; opaque to anyone without the Master Key; and independent of `keyEpoch`, so re-encrypting a version under a new epoch does not change its ID. A version record's header `hlc` is the `hlc` of the snapshotted state, so devices that store the same loser produce the same header. Each device keeps the 20 greatest `(hlc, versionId)` per item and drops a received version below that cut on arrival, and one belonging to a purged item once every record of the same transfer (a sync exchange or a backup merge) has been merged, so a restore from the trash that arrives together with its versions keeps them whatever their order (D137); every device thus converges on the same history. A conflict loser dropped by the cut triggers the notice described under Conflicts; this is a documented limitation for a device that edits an item while offline during more than 20 newer edits. Pruned and purged versions are dropped without a tombstone. Pruning is done while unlocked. **Old values stay in history (D135).** An edit does not remove the previous value: a changed password stays in up to 20 Item Versions on every device and in every later backup, and v1 offers no way to delete a version. To remove old values, the user duplicates the item (Duplicate writes its current content as a new item, with a new ID, no history and its title suffixed " (copy)" (D169), in the folder where the original is displayed, which is the vault root when the orphan rule applies, section 9.3, D156) and trashes the original, whose history is dropped at its purge; the item-history view states this. A trash and a restore from the trash each store a version like any other edit, so a trash-and-restore cycle uses two of the 20 slots with no new content; the item-history view states this too. **Duplicate and read-only items (D140).** Duplicate is blocked for an item that holds content from a newer app version (D52), and the UI tells the user to update the app, since its original could not be trashed afterward anyway; it is allowed for an item read-only only because its HLC is beyond the future-clock bound, since the copy takes a fresh HLC. Duplicate is not offered for an item in the trash until it is restored from the trash, as for restoring a version (D111). An Item Version header always has `deleted = false`; a received Item Version with `deleted = true` is rejected (D56). **Restoring a version (D111)** is an ordinary edit: it writes the version's content as the item's new state with a new HLC and stores the current state as an Item Version. A version of a trashed state holds a `trashOperationId`, which restoring the version drops, since only a trashed item carries one (D143). It is blocked while the version or the item is read-only (section 6), and offered for an item in the trash only after the item is restored from the trash.
- **Trash (D7, D27):** moving a record to the trash writes its tombstone. Purge date = physical time of the tombstone's HLC + 30 days, computed independently by each device. Purge is local: each device re-encrypts the record with empty content under the same header, so the header and `hlc` do not change and nothing is synchronized. Purge requires the vault to be unlocked. Only content and history are deleted; the tombstone remains. A tombstone received with content after its purge date is purged on arrival. Restoring from the trash is a newer write with `deleted = false`. A device whose clock is ahead purges early, on that device only; the content stays on the other devices until their own purge date, and this is accepted (D149). Purge is automatic only: v1 has no manual purge, because purge is local and a manual one would leave the content on every other device until its own purge date while the user believes it is gone (D94).
- **Network:** STUN is used only to assist connectivity. Default STUN providers are Google and Cloudflare; the user can replace them with a list of their own, kept for the installation and used by pairing, re-admission and reconnection (D209). STUN sees the public IP and MUST NOT be assumed to provide anonymity. A LAN-only mode without STUN MUST exist, for users who want network privacy; when neither side holds a capture permission (copy/paste pairing, reconnections), it depends on the local network resolving mDNS host candidates (D136, D161). Symmetric NAT, especially on some cellular networks, may prevent direct connections; v1 MUST NOT require TURN, and the fallbacks are same-network sync and `.bvault`. A future TURN mode MAY be considered only if it preserves the privacy model.

### 9.3 Folder tree rules (D14)

Each folder record converges independently through LWW, which can produce inconsistent trees. The tree is built at read time with these deterministic rules:

- **Cycles.** Concurrent moves (A into B on one device, B into A on another) can create a cycle. The folder in the cycle with the greatest `hlc` (D19) is displayed at the root.
- **Orphans.** An item or folder whose parent is a tombstone or is missing, including a parent not yet received, is displayed at the root. It moves under its parent once the parent arrives.

These rules never write records; once all devices have the same records, they show the same tree.

## 10. `.bvault` backup (D3)

The `.bvault` file gives offline recovery without any network service.

```
[magic][format version][parameters][phraseId, phrase creation date]
[keyslot: Recovery Phrase, crypto_box_seal]   ← mandatory (D16)
[keyslot: export password, Argon2id, fixed]   ← optional
[payload: secretstream(file key)]
    ├── encrypted records (as stored in IndexedDB), including the Recovery Envelope
    └── Master Key and vaultId (D25), wrapped by the file key
```

- The header carries magic, format version, cryptographic and key-derivation parameters, the `phraseId` of the recovery keyslot, and migration/versioning information; the header is authenticated and the payload is integrity-protected.
- A random file key encrypts the payload. Each keyslot wraps the file key, so either slot reaches the payload and the Master Key inside it. The recovery keyslot is sealed to the recovery keyslot public key from the Recovery Envelope (section 5.4), so a device can create it without the phrase.
- The Recovery Phrase **always** opens the backup. The export password is an extra path. Because the payload holds the Master Key, which v1 never rotates (D11), anyone who opens a backup with its export password holds the Master Key permanently: a weak or exposed export password is a Master Key compromise (section 14). The export password MUST reach an estimated 10^14 guesses or more (D134), above the local password's threshold, since a backup can be attacked offline wherever it is copied; the export UI offers a generated 6-word passphrase from the password generator (section 13.6) and MUST state this consequence (D36). A passphrase taken unchanged from the generator is checked against the same threshold by the generator's exact entropy rather than by zxcvbn, which can rate common BIP39 words lower and would reject the UI's own suggestion; once the user edits it, zxcvbn applies (D155). Its Argon2id parameters are fixed at the D9 floor (64 MiB, about 1 s on a mid-range phone), not calibrated on the exporting device, so a backup made on a desktop can be opened on a phone; the parameters are stored in the header. The header is authenticated only once a keyslot opens, so before running Argon2id a restore MUST reject parameters outside a fixed accepted range (memory from the 64 MiB floor up to a maximum, and a bounded `opslimit`); a tampered header then cannot exhaust a phone's memory. The exact export `opslimit` and the accepted range are fixed in `backup-format.md` (D78, D178).
- The outer layer hides IDs, HLCs and the number of records; the file size still reveals the vault's approximate size. A backup MUST remain encrypted when copied to untrusted storage.
- **Truncation and the header before opening (D95).** A restore MUST require the `secretstream` final tag (`TAG_FINAL`) on the last chunk and reject a payload without it or with data after it, so a truncated file never restores a valid prefix. The `phraseId` and phrase creation date are shown to choose a keyslot before any keyslot opens, when the header is not yet authenticated: the UI presents them as unverified until a keyslot opens and the header authenticates, and a tampered header fails that check and the file is rejected.
- **Export verifies before writing (D64).** Before writing a backup, the device verifies every record it holds as on receipt (section 9.2). If one fails, the export aborts, writes no file and names the record, so a corrupted local record is found at export, not at restore. The unlocked session holds no Master Key, so an export asks again for the local password, or a passkey assertion with user verification, and opens the Master Key wrap with it; the session builds the file itself and wipes the Master Key, file key and KEKs before returning (D181). While Local Config lists peers whose records were rejected for their format or type, the export warns that the backup may be incomplete (D68, D115).
- Automatic upload MUST NOT exist. The format is versioned and documented in `backup-format.md` (D178).
- **Restore** MUST support a **fresh restore** (onto a device that does not hold the vault: after device loss, after browser storage loss, or to install the vault on another device) and a **backup merge** into the existing vault when explicitly requested. A backup merge uses the same rules as sync. A backup merge MUST be rejected if the backup's `vaultId` differs from the local vault's (D13), or if the Master Key in its payload differs from the local one, compared in constant time, since `vaultId` is not secret (D57); every record then passes verification on receipt (section 9.2), and a fresh restore verifies every record the same way (D64). A restore is never applied in part: a fresh restore or backup merge holding a record with an unknown `recordFormatVersion` or a record that fails verification, or a backup merge holding a record beyond the future-clock bound or one that breaks the immutability of the Vault Key record or the Recovery Envelope (D42, D44), is rejected as a whole and writes nothing (D61, D64, D182). Restoring a different vault requires explicitly replacing the local one, after the same warning as erase (section 7), chosen from the unlock screen without unlocking (D183). A fresh restore of the same vault onto a device that holds it but cannot unlock it, as after a forgotten local password, also replaces the local vault after that warning, and commits in the existing database (section 7, D153). A fresh restore persists the records and the new Local Config in one storage transaction, as in pairing (D33). A restore opened with the Recovery Phrase MUST also open the Recovery Envelope in the payload with the phrase and reject the backup if that Master Key differs from the payload's; a restore opened with an export password ends by recommending Check Recovery Phrase (D43). After a fresh restore the device is an unregistered device: it has a new identity that other devices do not know, and it does not write its own Device record (D30); to sync with them it must be re-admitted (D22). After a fresh restore, if the vault holds Device records not marked retired, the UI SHOULD recommend re-admission with one of them, warn that until then this device exchanges data only through backups, and offer to mark devices that no longer exist as retired; Settings keeps that recommendation while the device stays unregistered (D186). An unregistered device gets its own Device record the first time it pairs another device (D30, D141).

## 11. Application integrity (D5)

- The service worker script (`sw.js`) is minimal and stable: it changes only when its own logic must, and each change is announced in the release notes. Application assets are served cache-first from a versioned cache. The script is written by hand, with no bundler and no dependency, so its bytes change only with its logic; the versioned cache is named by the asset manifest hash and filled at install from the asset manifest, each file checked against its SHA-256 (D190).
- **Asset updates (D63).** A new app version is an asset bundle. The running service worker fetches the new asset manifest, shows the version and the manifest hash, and switches to the new cache **only after explicit user confirmation**. The app never upgrades its assets silently. Applying an update locks the vault and then reloads the app, since the app never loads code after the first unlock (D142); the update prompt says the vault will lock, and the update is not offered while a pairing, re-admission, sync session, restore, import or re-founding is in progress (D152). The service worker looks for an update when the app starts and whenever it becomes visible, fetching and checking the new bundle as an install does; the build's `version.txt`, a listed file, gives the version (D191).
- **Limit of the service-worker lifecycle (D63, D142).** The browser fetches `sw.js` itself, outside the running service worker. A changed script runs its own code at install, with access to every cache of the origin, and can activate at once (`skipWaiting`) and take control of open app windows (`clients.claim`), so every later request of an open app window, one with an unlocked vault included, goes through it. A host that serves a different `sw.js` can therefore replace the application, and no page or service-worker code can prevent it. Two rules limit what it reaches in an app window already running: the app loads all its code and WebAssembly before the first unlock and never loads code afterwards (no runtime import, no lazily fetched chunk or `.wasm`), and when it detects a new service worker (`updatefound`) it locks the vault at once (section 7) and warns the user that the host served a changed service worker, which the release notes must justify, and that the app should not be unlocked again until the release is verified outside the app. This is detection, not prevention. The Phase 0 integrity spike confirmed the takeover on every browser of the matrix: `skipWaiting` alone switches an open app window to the new worker, and `updatefound` fires only 7–20 ms before it, so the lock MUST run synchronously in the `updatefound` handler, wiping key material before the handler returns, with no `await` before it. No browser looked for a changed `sw.js` on its own while a page stayed open, so the app calls `registration.update()` whenever it becomes visible: a changed `sw.js` is then detected when the user returns, before any input, which does not widen the exposure since the browser fetches `sw.js` at the next navigation anyway (D162).
- Reproducible build with pinned lockfile and Node version and `SOURCE_DATE_EPOCH`, to make application integrity verifiable. CI rebuilds and compares the hash. The asset manifest is `asset-manifest.txt` at the root of the build, in the `shasum -a 256` format, and its hash is the SHA-256 of its bytes; `docs/build.md` specifies both and how to rebuild and compare (D189).
- The asset manifest hash (SHA-256) is published on GitHub Releases and displayed in the app together with the running version. The hash a build displays about itself is informational only, since a malicious bundle can display any value. The About screen shows both, from Settings and before unlock (D192). The hash of an asset update, computed by the running service worker before switching, catches an asset change that does not come with a new `sw.js`. The decisive check is verification outside the app: rebuilding from source, or comparing the served assets and `sw.js` with the release.
- **Content security (D83).** The app MUST ship a strict Content Security Policy, delivered by `<meta>` so it works on static hosts that cannot send headers; a self-hosted deployment SHOULD also send it as a header. It starts from `default-src 'none'` and allows only what the app needs (D91): no inline script and no `eval` (`script-src 'self' 'wasm-unsafe-eval'`, the latter for libsodium's WebAssembly), `style-src 'self'`, `img-src 'self' data: blob:` (QR rendering), `worker-src 'self'`, `manifest-src 'self'`, `connect-src 'self'`, `object-src 'none'`, `base-uri 'none'`, `form-action 'none'`, and requires Trusted Types (`require-trusted-types-for 'script'`) where the browser supports them. The CSP also enforces that no network call can carry vault data; WebRTC is not governed by CSP and stays limited by section 9. Item content is untrusted input: it is always rendered as text, never as HTML, and a URL field opens only `http:` and `https:` URLs. A URL field opens with `noopener` and `noreferrer`, so the opened page gets no `window.opener` and cannot navigate the app's window to a fake unlock page, and the app ships `<meta name="referrer" content="no-referrer">`, so no Referer header reveals the app's origin (D147). `frame-ancestors` cannot be set by `<meta>`, so the app MUST NOT open inside a frame: when `window.self` is not `window.top`, it shows only a notice with a link that opens it in its own tab, and it opens no IndexedDB database, takes no Web Lock, starts no worker and registers no service worker (D193); hosts that can send headers also set `frame-ancestors 'none'`, and `Cross-Origin-Opener-Policy: same-origin`, so a page of another origin that opens the app keeps no handle on its window (D195).
- **Dedicated origin (D90).** The app MUST be served from an origin that serves nothing else. On GitHub Pages this requires a custom domain dedicated to the app: a project site under `<user>.github.io/<repo>` shares its origin with every other Pages site of that account, and so does the account's root site. Same-origin content can read and delete the vault's IndexedDB, take its Web Lock, and script an unlocked app window it opens, which the frame check does not stop. A self-hosted deployment has the same requirement. At startup the app SHOULD warn when it runs under a sub-path of a `github.io` host, a shared origin; the check catches a misconfigured deployment, not a malicious host.
- Static self-hosting MUST work, so a user who does not trust the official host can build and host BlindVault independently. `docs/self-hosting.md` states the requirements, and the configurations of `deploy/` for Caddy and nginx are tested in CI (D195).
- The first load relies on trust on first use, and so does every change to `sw.js`; this is recorded in the threat model.

## 13. User interface

### 13.1 Layouts (D15)

Unlike BlindPass, which uses a single mobile layout everywhere, BlindVault has a dedicated layout per form factor.

| Layout | Available width | Structure |
| --- | --- | --- |
| Mobile | < 640 px | One column with drill-down navigation: folders → items → item detail. Bottom navigation |
| Tablet | 640–1023 px | Two panes: item list and item detail. Folder tree in a collapsible drawer |
| Desktop | ≥ 1024 px | Three panes: folder tree sidebar, item list, item detail |

- Layout is chosen by **available viewport width**, never by user-agent or device detection. A narrow desktop window shows the mobile layout; a tablet in landscape may show the desktop layout. Changing width switches layout without losing state or locking the vault: the three shells place the same panes in one component tree, so nothing remounts (D197).
- On mobile, the browser's or the system's back takes the app one screen back, through a single history entry that carries nothing (D197). On tablet, the folder drawer opens over the item list.
- A write that ends by moving to another screen (saving an item, duplicating it, restoring a version, creating a folder) moves only if the screen it started from is still shown; if the user went elsewhere meanwhile, the write completes and the panes refresh, and the user stays where they went. Each New item opens a fresh template picker (D210).
- **Input adapts separately from layout**, using `pointer` and `hover` media queries: touch targets of at least 44 px on coarse pointers, hover affordances only where hover exists, and keyboard shortcuts (search, new item, lock) wherever a keyboard is used, whatever the layout (D197).
- One set of domain state and components, with three layout shells. Layout code MUST NOT duplicate business or security logic.
- **Security rules are identical in every layout.** Secrets stay masked by default even when wider layouts show more at once, revealing requires an explicit action, lock/unlock state is always visible, and auto-lock behaves the same.
- The UI security requirements (section 13.2) apply to all three layouts.

### 13.2 UI security requirements

The UI MUST:

- clearly indicate locked/unlocked state;
- avoid displaying secrets unnecessarily;
- keep every vault identifier (item, folder or record ID) and every piece of vault content out of the URL and the browser history, which persist outside the vault's storage: navigation state lives in memory only, and the one history entry the app pushes for the system's back carries no state (D167, D197);
- keep vault content out of the browser's form history, which also persists outside the vault's storage: every text field turns autocomplete off, except the local password fields, which name their purpose (D174);
- turn spellchecking off in every text field, since a browser's enhanced spellchecker, when the user enables it, sends what is typed to a remote service (D176);
- mask secret fields by default, including a TOTP field's TOTP secret and a seed-phrase field; a TOTP field's current code is shown unmasked, since it expires within its period (D127);
- require explicit action to reveal secrets;
- copy a secret, or a TOTP field's current code, only on explicit action, and try to clear the clipboard after a timeout (30 s by default, configurable from 10 to 120 s and never turned off, D151) while the app has focus, stating that clearing is not guaranteed (D54, D127);
- lock after the app has been hidden for the configured time (section 7, D54);
- provide clear backup and recovery warnings;
- clearly show synchronization state;
- show the last successful backup made on this device and the last successful synchronization;
- warn about storage persistence problems: Safari in a plain tab, storage not kept on the only device, and storage nearly full (D196).

### 13.3 Onboarding

A new installation offers three starts. The flows SHOULD be:

```
Create vault → Generate Recovery Phrase → Confirm Recovery Phrase → Create local password
→ Optional WebAuthn setup → Vault ready → Recommend backup → Recommend pairing another device

Pair with an existing device → Create local password → Pairing (section 8.4)
→ Optional WebAuthn setup → Vault ready → Recommend backup

Restore from backup → Choose .bvault → Recovery Phrase or export password → Create local password
→ Optional WebAuthn setup → Vault ready → Recommend Check Recovery Phrase (export password only, D43)
→ Recommend re-admission, or pairing another device if no Device record is left unretired (section 10)
→ Recommend backup
```

On Safari, before the three starts, the app recommends installing it first, since the installed app does not share the tab's storage (section 7, D103); "Continue in this tab" shows the starts (D198). Every start generates the device identity and requests persistent storage (section 7). Creating the vault also writes the creator's own Device record; pairing and restore do not (D30).

Onboarding MUST explain that BlindVault has no server that can reset the user's vault, which is why the Recovery Phrase is critical. The first screen says so before the starts (D198).

**Vault ready (D198).** After a creation, a restore or a pairing (D203), a "Vault ready" screen lists the recommendations above, in order, each with an action that opens Settings at its section, and "Open the vault" closes it. The optional WebAuthn setup is the first of them, offered only where the browser supports it: setting it up needs the local password, which is not kept from the password step. The pair start creates the local password and runs the pairing as the joining device (section 8.4), which ends on "Vault ready" with passkey unlock and a backup; the pairing recommendation after a creation or a restore opens the pairing in Settings (D203).

### 13.4 Backup reminders

The application MUST record, in Local Config, the date of the last backup made on this device and the last synchronization date, and SHOULD warn when the backup interval expires. The date is local and not synchronized, so the UI MUST present it as "last backup made on this device". In v1 the interval is a fixed 30 days, with no setting (D188).

### 13.5 UX principles

BlindVault favors explicit security decisions, understandable warnings, safe defaults, minimal configuration and clear recovery flows. Security-critical operations MUST NOT be hidden behind ambiguous UI.

### 13.6 Password generator (D128)

The item editor offers a password generator in two modes: random characters from the selected character sets, and a passphrase of words from the BIP39 English list that `@scure/bip39` already ships. Every choice comes from libsodium's CSPRNG through `randombytes_uniform`, which has no modulo bias. The generator shows the entropy of its settings in bits. Defaults: 20 characters from all four character sets (lowercase, uppercase, digits, symbols), or 6 words (about 66 bits). Minimums: 12 characters or 4 words; below them the generator offers no value. Every character is drawn uniformly from the union of the selected sets, with no guarantee of one character per set, which keeps the entropy display exact; the user generates again if a site requires each set (D138). A generated value exists only in the field being edited until the item is saved; the generator keeps no history and persists no generated value. Its settings (mode, length, character sets, word count) are non-sensitive UI preferences.

## 14. Recovery

| Situation | Recovery |
| --- | --- |
| Local password forgotten | The Recovery Phrase whose envelope this device holds sets a new password from the unlock screen (D173, D184), which is the old phrase if it was regenerated elsewhere and this device has not synced since (section 5.4); it keeps changes that exist only on this device. WebAuthn unlock, if set up, still opens the vault meanwhile, for a backup, but sets no password. Otherwise replace the vault by pairing with another device or by a fresh restore of a backup (D153), which loses them; mark the old Device record retired |
| Device lost | Pair a new device, or restore `.bvault` and re-admit it (D22); mark the lost device retired (D30). If that device's local password or its WebAuthn user verification was weak (D75), or the device was unlocked when lost, treat it as a Master Key compromise |
| All devices lost | `.bvault` + Recovery Phrase; mark the old devices retired (D30) |
| Browser storage erased | Pair again with another device, or restore `.bvault` and re-admit it (D22); mark the old Device record retired (D30) |
| Recovery Phrase lost | Regenerate it while unlocked (section 5.4), then make a new backup |
| Device clock was set far ahead, then corrected (D149) | The vault stays read-only until the clock passes the greatest HLC it issued. Copy by hand any value changed with the wrong clock, then replace the vault by pairing with another device (D153), or re-found the vault (D28) |
| Recovery Phrase exposed | Master Key compromise: re-found the vault (D28), pair the other devices again, destroy old backups |
| Export password exposed, with its backup (D36) | Master Key compromise: re-found the vault (D28), pair the other devices again, destroy old backups |
| Unexpected retirement or unknown device in the new-device notice (D47, D48) | Master Key compromise: re-found the vault (D28), pair the other devices again, destroy old backups |
| Master Key compromised (D11) | Sync every device still in hand with one of them, re-found the vault there (D28, D46), pair the other devices again, destroy old backups |

**Re-founding (D28).** The v1 response to a Master Key compromise, in place of Master Key rotation (D11). On an unlocked device, retired or not (D47), re-founding keeps the vault's current content under entirely new keys. Before it starts, the UI MUST tell the user to sync this device with every other device still in their hands, and state that changes not on this device are lost, and that the trash and every item's history are emptied, with an offer to restore anything still needed from the trash first (D72): other devices must be replaced by pairing afterwards (D150), and a backup merge of the old vault is rejected because its `vaultId` differs (D46). If Local Config lists peers whose records this device rejected for a newer format or an unknown type, the UI MUST also state that those records are not on this device and will be lost, name those peers, and recommend updating the app and syncing with them first; re-founding proceeds only after explicit confirmation (D116). A retired device cannot sync first, so on a retired device the UI MUST state that changes existing only on other devices are lost, and recommend re-founding on a non-retired device if one is still in the user's hands (D47). Syncing from a possibly compromised device adds no risk, since its holder already has the Master Key. Re-founding:

- asks again for the local password or a passkey, after the warnings and before the new phrase (D187);
- generates a new Master Key, `vaultId`, Vault Key and Recovery Phrase; the user confirms the phrase as at creation and sets the local password again (new Local Config);
- re-encrypts every Item and Folder that is not a tombstone under new random IDs, new record keys and new HLCs, and rewrites every `folderId` and `parentId` to the new IDs, so the old and new vaults' cleartext headers cannot be matched (D99);
- moves to the vault root every item and folder whose parent folder is not carried over, removing its `folderId` or `parentId`, so no reference points outside the new vault; a read-only item keeps its content unchanged (D60) and shows at the root by the orphan rule (section 9.3) (D86);
- drops history, tombstones, the trash and every Device record, generates a new device identity, and writes its own Device record as the creator of the new vault (D40);
- carries read-only items over with their decoded content unchanged, unknown keys included, and gives them fresh HLCs like every other record (D60);
- builds the new vault in memory, writes it encrypted to its own database and commits it with its Local Config, then deletes the old database (D89), so plaintext is never persisted and an interruption before the commit leaves the old vault intact;
- ends as vault creation does: Optional WebAuthn setup → Vault ready → Recommend backup → Recommend pairing, since the new vault has no backup and no other device yet. WebAuthn unlock of the old vault stops working, since its wrap is bound to the old `vaultId` and was deleted with the old Local Config (D107).

Other devices still hold the old vault and can no longer sync with this one; each must be replaced by pairing with the new vault (D150). Old backups open the old vault with the old phrase and MUST be destroyed. Re-founding protects only what happens afterwards: an attacker who already copied the old vault keeps it, and the UI MUST say so.

There is no administrator recovery, hidden or otherwise. Losing all data and all recovery mechanisms means permanent loss, and this MUST be communicated to users.

## 15. Import and BlindPass reuse

**Import (D123).** v1 SHOULD import items from the export files of other password managers, the same formats BlindPass imports:

| Source | File |
| --- | --- |
| BlindPass | Its own export: plaintext `.json` or encrypted `.blindpass` |
| Chrome, LastPass, Apple Passwords, KeePassXC | CSV |
| Bitwarden, Proton Pass | JSON |
| 1Password | `.1pux` (zip) |
| Dashlane | `.zip` |

BlindPass data comes only from BlindPass's export files, never from BlindPass's stored representation, which lives behind its server and keychain. BlindPass exports carry items only, so BlindPass collections are not imported. The BlindPass export format is documented in `blindpass-format.md`.

**`.blindpass` decryption (D126).** A `.blindpass` export is decrypted with a key from Argon2id at libsodium's `SENSITIVE` limits (1 GiB of memory), which BlindPass fixes in code and does not store in the file, followed by `crypto_secretbox` (section 5.1). The parameters are therefore constants in BlindVault, never read from the file. The Phase 0 Argon2id spike measures whether 1 GiB runs on each browser of the matrix; where it does not, the UI says so before deriving and tells the user to import on another device and sync.

The import MUST:

1. read the source file only in memory and never persist it or any plaintext derived from it;
2. validate the source data, rejecting a file whose shape does not match its format with a message the user can read;
3. transform it into BlindVault's domain model (below);
4. encrypt the resulting records with BlindVault's cryptographic format, like any other write.

Every format except `.blindpass` is an unencrypted file on the user's disk. v1 reads only the unencrypted exports of Bitwarden and Proton Pass: an encrypted Bitwarden export or a PGP-encrypted Proton Pass export is detected and rejected with a message telling the user to export unencrypted (D146). Before the user chooses a file, the UI MUST state that a plaintext export exposes every secret it holds, and after the import it MUST tell the user to delete the source file.

**Mapping (D124).** Field types replace BlindPass's workarounds for its fixed item types:

- A source TOTP becomes a `totp` field of the same item; no separate item is created. A source value that parses as an `otpauth://` URI becomes a `totp` field, whatever its key. A bare base32 value becomes a `totp` field only under a TOTP-looking key (`totp`, `otp`, `2fa`, `mfa`, `authenticator` and similar), since many real passwords and words are valid base32; under any other key it keeps the type its key gives it. Any other value under a secret-looking key, "TOTP" included, becomes a `secret` field (D131, D133).
- A source category with no matching factory template becomes a Secure Note titled `[Category] Title`, its source fields kept as typed fields (section 6).
- A source field whose key looks secret (password, secret, mnemonic, recovery phrase, private key, TOTP, PIN, CVV and similar) becomes a `secret` field, masked like any other, and is never dropped.
- Attachments come after v1 (section 20): a source attachment is dropped, counted, and named in the item's notes (`[Lost attachments: …]`).

**Landing folder and commit (D125).** Every import goes into one new folder at the vault root, `Imported from <source> <date>`. Source folders, groups or vaults become subfolders of it, and source tags become tags. Nothing is merged into the user's existing tree, and importing the same file again creates a second folder; there is no deduplication. The import first parses the whole file and shows a preview (items found, items skipped, including those above the item cap (D129, D139), attachments dropped, categories turned into notes); on confirmation it writes every item and folder in one storage transaction, with new IDs, new HLCs and no history. A lock of any kind before the commit aborts the import and writes nothing (section 7). Import is not offered while the vault is read-only because the device clock went back (section 9.2).

**Placement (D125).** Parsers and mapping live in `packages/vault`, as pure code with no IndexedDB or network access; decryption of a `.blindpass` export lives in `packages/crypto`; reading the file stays in `apps/web`. The zip formats use `fflate`, justified in `architecture.md`. The source file is untrusted input: any import file larger than 100 MB is rejected before parsing, and a zip archive is also rejected beyond 100 MB of total uncompressed size or 10,000 entries (D130).

**Code reuse.** BlindPass cryptographic and domain code is **copied** into the matching BlindVault package, never imported at runtime or linked as a dependency. Where BlindPass differs on a primitive, AAD layout, key hierarchy or serialization, this document wins and the difference is recorded in `architecture.md`. Copied cryptographic code gets the same tests and review as new code. The BlindPass server application, API schema, PostgreSQL, Redis, Docker and Terraform code are not reused.

## 17. Security invariants

| ID | Invariant |
| --- | --- |
| CRYPTO-INV-001 | Plaintext vault contents MUST NOT be persisted |
| CRYPTO-INV-002 | The Master Key MUST NOT be synchronized in plaintext |
| CRYPTO-INV-003 | The Master Key MUST NOT be stored directly in IndexedDB |
| CRYPTO-INV-004 | Every encrypted record and tombstone authenticates its `recordFormatVersion`, `recordType`, `vaultId`, `recordId`, `keyEpoch`, `hlc` and deletion state via AAD |
| CRYPTO-INV-005 | Keys MUST NOT appear in logs |
| CRYPTO-INV-006 | Recovery material MUST NOT be logged or persisted in plaintext |
| CRYPTO-INV-007 | A Device record is created only for the vault creator at creation or re-founding (D40), or after explicit SAS confirmation (D30); afterwards only its display name and `retired` flag change |
| CRYPTO-INV-008 | Before syncing, a peer proves possession of its registered identity (Noise_KK) |
| CRYPTO-INV-009 | Every sync message is authenticated and bound to the active session |
| CRYPTO-INV-010 | Secrets are removed from application-accessible memory on lock, as far as JS permits |
| CRYPTO-INV-011 | No Master Key or recovery secret is transferred before SAS confirmation on both devices (D148) |
| CRYPTO-INV-012 | Unknown or incompatible format and protocol versions, and unknown record types (D81), are rejected, never interpreted as compatible |
| CRYPTO-INV-013 | Within a vault, a tombstone is never removed in v1, and a write older than a record's tombstone never brings it back (re-founding creates a new vault, D28) |
| CRYPTO-INV-014 | Re-admission writes no Device record until both devices prove, bound to the session, that they hold the same Master Key (D29) |
| CRYPTO-INV-015 | No sync summary or record is exchanged with a peer whose Device record is retired, except that peer's own retired Device record (D45), and a retired Device record never becomes non-retired (D31) |
| CRYPTO-INV-016 | Vault Key, Recovery Envelope, Device and Item Version records are never accepted with `deleted = true` (D42, D56), a held Vault Key record is never replaced by a different key (D42), and a held Recovery Envelope is never replaced by one with the same `phraseId` and a different `hlc` or metadata (D44) |
| CRYPTO-INV-017 | At most one app window per installation opens the vault and writes records (D51), and at most one creates, replaces or deletes a vault database (D97); none deletes or replaces a vault database while another app window holds that vault's Web Lock (D154) |
| CRYPTO-INV-018 | No received record is merged or persisted, through sync, backup merge or fresh restore, unless its wrapped record key and content authenticate under the vault's keys and its derived `recordId` matches (D57, D64, D66); a restore holding a failing record writes nothing, no backup is written while a held record fails this check (D64), and a backup merge whose payload Master Key differs from the local one is rejected (D57) |
| CRYPTO-INV-019 | Local Config holds nothing in cleartext beyond its format version (D164), `vaultId`, `localConfigId` (D121), local KEK material, PRF KEK state and, until the replaced database is deleted, the replaced `vaultId` (D96); the rest is authenticated encryption under a Master Key subkey (D58) |
| CRYPTO-INV-020 | A device never issues an HLC that is not greater than every HLC it issued before; while the future-clock cap would require one, it issues no new HLC, and so makes no write that needs one, except a retirement, which takes its HLC state with its counter incremented (D62, D73, D85) |
| CRYPTO-INV-021 | The PRF KEK is derived only from a WebAuthn assertion with user verification (D75) |
| CRYPTO-INV-022 | No record whose `hlc` is beyond the future-clock bound is merged in sync or backup merge; one accepted beyond it in a fresh restore or a pairing's first full sync is read-only until within the bound (D19, D39, D76, D101, D114) |
| CRYPTO-INV-023 | Every local wrap authenticates its purpose, `vaultId` and `localConfigId` via AAD, so a wrap does not open under another purpose, vault or Local Config (D121) |

## 19. Rules for AI agents

This document is **normative**.

**Agents MUST NOT:** invent cryptographic primitives; replace a specified primitive or protocol without explicit approval; weaken authentication for convenience; persist plaintext secrets for debugging; add telemetry containing vault data; add a backend to simplify sync; silently change the key hierarchy or the backup format; remove security checks to make tests pass.

**Agents SHOULD:** read package boundaries before changing a package; batch-read related files when investigating architecture; preserve the invariants; add tests for all security-sensitive behavior; explain any security-model change **before** implementing it.

### Definition of Done for security-sensitive changes

1. Design documented.
2. Relevant invariant identified.
3. Implementation complete.
4. Negative tests exist.
5. Migration implications understood.
6. Protocol or version changes documented.
7. Existing tests pass.
8. No plaintext secret handling introduced.
9. Threat-model implications reviewed.

## 20. Out of scope for v1

- **Device revocation**, deferred because it is complex and of limited benefit: revocation cannot erase data already replicated, and rotating the vault key only protects data encrypted afterwards. `keyEpoch` is already reserved. A future revocation SHOULD: revoke the device → new key epoch → new vault key → re-encrypt active data → exclude the revoked device from future sync. Because the Vault Key record is wrapped by the Master Key, which a revoked device holds, a new key epoch alone does not exclude it: revocation MUST either distribute the new Vault Key only to remaining devices (wrapped to each device's static key, with the Recovery Envelope handled accordingly) or rotate the Master Key (revisiting D11). The Recovery Envelope's Master Key wrap is bound to the envelope's header through the AAD, including `keyEpoch` and `hlc`, so moving the envelope to a new epoch rewrites that wrap and needs the Recovery Phrase or a regeneration; a future revocation design MUST account for this. Documentation MUST keep stating that previous copies cannot be remotely erased.
- **Master Key rotation** (D11). Re-founding (D28) is the v1 response to a compromise.
- **Attachments** (up to 10 MB, chunked `secretstream`, encrypted blob sync, storage quota management), deferred to keep v1 simple. They MUST NOT complicate the basic sync protocol. Improved backup workflows come with them.
- **Shared vaults** (D80). Sharing between people requires a different trust model and MUST NOT reuse device pairing. The direction is fixed by D80: a shared vault is a vault kind fixed at creation, and the whole vault is the unit of access. Members are represented by Member records listing their device identities, and every device receives the current epoch's Vault Key wrapped to its identity. Only Admins hold the Master Key and the Recovery Phrase, and only they make backups; this MUST NOT be presented as protection against exfiltration, since every Member reads every item. Membership changes are signed by an Admin, except that a Member's device MAY admit another device of the same Member, with SAS confirmation, a signature by that device and a notice to Admins. Joining is a new SAS-confirmed admission protocol, distinct from pairing, that transfers only the Vault Key; remote invitations come later. Every write is signed by its writing device, which gives authenticated attribution. Removing a Member starts a new key epoch for future writes without re-encrypting existing records, and the UI lists the items whose real credentials the Admin should change. Removing an Admin replaces the Master Key in place (revisiting D11 for shared vaults only). A shared vault has at least one Admin, the last Admin cannot remove themselves, and a single Admin is warned to add a second. Shared vaults depend on multiple vaults (D79) and on the signaling relay (D12). Each of these needs its own specification (admission protocol, signed record format, Member record, in-place Master Key replacement, multi-member relay sync) before implementation.
- **Browser extension and autofill**, which are a separate security boundary with a much larger attack surface.
- **Cloud storage plugins** (Drive, Dropbox), which would only receive `.bvault`-format data. The core app MUST remain functional without them.
- **TURN.**
- **Clipboard history and sync** (OS clipboard history, cloud clipboard), which the app cannot control (D54).
- **Signaling relay for automatic sync** (D12): mailbox interface with Nostr and ntfy adapters, off by default, no official instance. Must never receive vault data.
- **User-created templates**, which will use the reserved `Template` record type (D20).
- **Multiple vaults** (D79). An installation MAY hold several vaults, personal or shared, each with its own device identity, Local Config, local unlock and Web Lock, so a peer of one vault cannot link the device to another. One vault is unlocked at a time; switching locks the current one and unlocks the target. A switcher shows each vault's Vault nickname, kept in cleartext on that device only and never synchronized. Pairing and fresh restore add a vault to the installation instead of requiring it to be empty. Items cross vaults only by "Copy to vault": the decrypted content of one item is held in memory across the switch and written as a new item, with a new ID and no history; the source is unchanged and there is no move. A personal vault never becomes a shared vault; the user creates a shared vault and copies items into it.
